# 多参参考槽：9 是界面上限，不是模型上限

> **状态（2026-10-22 当日，已被下一条取代）**：本文的**排查结论仍然成立**（模型侧没有 9 张限制、每张参考图约 1008 个 packed token）。但「决定」一节里的**执行部分当日作废**——用户实测后认定多参路线本质仍是「首帧生成视频」，不再为多参单独铺机制，spec #64 及其全部子票同日关闭（见该 spec 的关票评论）。
>
> **状态（2026-10-25 更新）**：排查结论仍然成立，但**「9 的权威口径」与「决定」两处都要更正**。9 不只是节点 UI 上限，**同时是官方 API 的单次请求上限**（≤9 图 + ≤3 视频 + ≤3 音频、总文件 ≤12，spec #84 D5 / issue #86——代码里那句「9 不是旧节点的 UI 上限」说的就是不要把 9 只读成界面限制）；24 槽扩槽只跑过实验臂，16GB 卡上 24 张全喂实测 OOM，故登记工作流回到「59-(多Lora改)MiniMax-H3 ref2va 多参生视频 V2」的 9 图槽版本，24 槽节点包与 V3 工作流从**仓库**退役（issue #90，见文末「2026-10-25 处置」），本机件保留。

2026-10-22 的一次真实运行产出了 **24 张素材图**，而登记工作流「59-(多Lora改)MiniMax-H3 ref2va 多参生视频 V2」只有 9 个图片参考槽。超出的 15 张在注入卡上被标成「无对应槽位」（`injection_card.py:340-343`、`377-384`），用户在多参路线里**无端口可接，视频无法继续生成**。此前 `_SLOT_COUNTS` 把 9 当作物理事实写死（`injection_card.py:272`），这次运行说明了它的后果。

## 9 是谁定的

排查结论（2026-10-22，本机 `D:\Comfyui\ComfyUI`）：

- **模型侧没有 9**：`minimax_refs` 是任意长度列表，`PackedLayout` 按 refs 数量逐项追加 token 段（`comfy/ldm/minimax/model.py:396-439`），`model_base` 只做搬运（`comfy/model_base.py:2204-2208`）；全目录没有 assert、没有 `[:9]`、没有固定槽位张量。
- **9 是节点 UI 上限**：官方节点 `Autogrow.TemplatePrefix(..., max=9)`（`comfy_extras/nodes_minimax_h3.py:269-272`）；上游 PR #16076 原话称其为「the current nine-image UI limit」。
- **9 被复制了三层**：JZL 固定总线 `BUS_KEYS` 的 `range(9)`（`nodes_ref2va_bus.py:16`）、H3 固定节点逐个列出的 `ref_image_0..8`（`nodes.py:234-242`）、调度器 `if i >= 9: break`（`story_nodes.py:507-509`）。
- 本机工作流 1141/1142 的「多图槽」**不是喂 20 张**：24 张图进 48 槽素材总线，再由 `SceneDispatcher2` 每段选 ≤9 张。9 作为**每段默认值**仍然合理，作为**全局容量**才是错的。

## 决定

1. **新建本地节点包**（`custom_nodes/MiniMaxH3-Refs24/`），提供 24 个图片槽的总线与 H3 编码节点，内部复用上游同一套编码逻辑；**不就地改** `ComfyUI-JZL-MiniMax-H3` 的 Python——那是第三方目录，上游更新会覆盖，与已有的 ComfyUI 本地补丁是同一类维护负担。
2. **新建工作流 V3**（保留 V2 作退路），仓库登记名同步为 V3。
3. **仓库侧槽位数改为配置项**（`config/workflow.yaml`），注入卡按配置判越界；不再写死常量。
4. **分期**：P1 先「扩槽 + 每段全喂」，让 24 张当天能跑；P2 再做「按段调度」（`SceneDispatcher2` 每段选 ≤9），后者必须把分段提示词的 `<Picture N>` 与 `<Subject N>` 改为**段内编号**，牵动校验器、`plan.json`、续跑与「全片共享同一批参考素材」的模板措辞。

## 代价（写进卡与文档）

`ref_image_size="match"` 下每张参考图约 **1008 个 packed token**（≈目标视频一个 latent frame）。9 张约 +24%，24 张约 +65%；参考行每一步都参与注意力，成本超线性，Qwen3-VL 还要逐张编码。16GB 显存上 24 张全喂有 OOM 或慢数倍的风险——P1 的验收必须包含实测耗时与显存。

## 考虑过的备选

- **只改工作流 JSON**：不行。端口由 Python 的 `BUS_KEYS` / `Input(...)` 生成，JSON 里多写一个名字不会产生端口，图会被静默丢弃。
- **设计阶段限量到 9**：等于让设计迁就接线，而 24 张是剧本实际需要——否决。
- **只做按段调度、不做扩槽**：每段 ≤9 本来就能跑，但它要求分段提示词立刻改段内编号，用户这几天仍然跑不了；分期把「能跑」与「省资源」分开。
- **就地改 JZL 文件 / fork 整个节点包**：前者升级即丢，后者要跟一整个第三方仓库。
- **把 9 当作模型能力**：排查已证否；但把它当每段默认值仍然合理（1142 的社区做法）。

## 后果

- 注入卡恢复「逐条映射」的完整形态（全局编号 1..24 → `ref_image_0..23`），用户一次接线。
- P2 未落地前，「全片共享同一批参考素材」的措辞仍然成立；P2 落地时要逐处改（`segment_prompts.py:1120`、`prompts/segment_planner_ref.md`、`ref_segments.py:257`）。
- 新节点包与 V3 工作流是**本机件**，不进仓库；仓库只记工作流名、槽位数与代价。（2026-10-25 更正：当时在 `docs/comfyui/` 留的节点源码副本、工作流副本与两个脚本**已随 24 槽退役删除**，见文末「2026-10-25 处置」——「不进仓库」与「仓库留副本」本来就是两种口径，退役时按前者收口。）
- 24 槽是本次真实需求的边界；素材数再涨时先量显存与耗时，再决定扩槽还是按段调度。（2026-10-25 实测答案：不扩槽，改按段取用 ≤9 张。）
