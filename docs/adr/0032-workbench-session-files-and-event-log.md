# 工作台会话以文件为真源，事件流走 JSONL + 单调序号

> **状态（2026-11-09 复核）**：已接受；D2 起生效，适用于本机单用户工作台。

D2 要把生成会话从终端向导里抽成可查询、可恢复的服务端状态机。会话状态每推进一个节点就要落盘，前端要能看到「当前状态 + 发生过什么」，崩溃后还要能对账。可选的真源有两种：本机数据库（SQLite）或每个会话一个目录、目录里放 JSON 快照与追加式事件流。我们选择后者。

## 决定

1. **一个会话 = `sessions_root` 下的一个目录**（`<主题slug>/GEN00N/`）。`session_id` 就是相对 `sessions_root` 的路径；目录布局因此成为对外契约的一部分。
2. **`session-state.json` 是快照**，schema 为 `workbench.v1`，带 `status`、`revision`、`last_event_seq`、最近任务摘要与待办列表。
3. **写入一律「临时文件 + `os.replace`」**。同目录临时文件保证替换发生在同一文件系统内；中途被杀只留旧快照，不留半截文件。
4. **`events.jsonl` 是事件流**，一行一事件、只追加；`seq` 在会话内从 1 开始严格单调。事件只是记录、不是命令，因此重放幂等。
5. **先写事件、后写快照**。两者之间崩溃时，快照的 `last_event_seq` 落后于事件文件尾号；加载时重放 `seq > last_event_seq` 的事件即可补齐。跨文件没有事务，这是有意的取舍。
6. **不轮转、不裁剪事件文件**。单会话量级是几十到几百条，相比视频与图片产物可以忽略；具体上限实测后再定，不预先虚构阈值。

## 考虑过的备选

- **SQLite**：事务、索引、并发控制都是现成的，跨会话查询也方便。拒绝它的理由不是「数据库不好」，而是当前问题不需要它：单机、单用户、单进程，每个会话已有进程内互斥；会话的产物本来就是文件，用户会直接打开目录、拷贝、删除，数据库会引入第二份「会话里有什么」的真相，且备份/迁移从「拷目录」变成「导出 + 拷文件」两步。将来若出现多人、远程或跨会话检索，再评估迁移。
- **只用一个不断覆写的大 JSON**：没有事件序号就无法做 `Last-Event-ID` 补发，也无法在崩溃后区分「快照旧了」与「事件丢了」。快照 + 事件流的两层结构正是为了这两个能力。
- **每个事件一个文件**：目录项数量随会话长度增长，列举与清理都更贵；JSONL 的顺序追加与逐行读取更简单。
- **把事件流放进快照 JSON 数组**：每次追加都要重写整份数组，写放大且失去「只追加」的崩溃安全性质。

## 后果

- `session_id` 与目录布局绑定：改布局就是破坏对外契约。这是 D2 spec §5.1 明写的取舍。
- `events.jsonl` 与快照可能短暂不一致；消费方必须按 `last_event_seq` 对账，不能假设两者永远同步。
- 原子替换只保证单文件完整，不保证多文件事务；任何跨文件不变量都要能由「事件重放」恢复。
- 事件序号是会话内口径，不是全局口径；需要跨会话排序时必须另加时间戳或全局序号。
- 历史 `wizard_session.v1` 会话不迁移：它们按 legacy 只读处理，不参与事件流，也不能被工作台推进。
