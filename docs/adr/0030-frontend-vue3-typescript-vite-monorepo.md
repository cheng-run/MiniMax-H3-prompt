# 前端采用 Vue 3、TypeScript 与 Vite，并与 Python 后端同仓

> **状态（2026-11-09 复核）**：已接受；适用于从零建设的 Web MVP 与后续桌面外壳。

本项目是个人项目，已有稳定的 Python 生成内核，但没有前端存量。界面以多步骤表单、会话状态、任务进度和媒体审阅为主，不是需要 SSR/SEO 的公开站点。在当前“Python 后端先行、后续逐步补前端”的条件下，我们在 React 与 Vue 3 之间选择 Vue 3，并把前端放在现有仓库的 `frontend/` 下。

## 决定

1. 前端使用 Vue 3 Composition API、TypeScript 严格模式与 Vite，不用 Vue 2，也不以纯 JavaScript 实施。
2. Python 后端、前端、契约生成与端到端测试继续住在当前 monorepo；API 由 FastAPI 暴露并生成 TypeScript 客户端。
3. 浏览器 Web MVP 是正式产品代码；桌面 EXE 复用同一套前端，不建立第二套 UI。
4. 业务状态和状态机归 Python 服务端，Vue 侧只持有服务端视图、局部 UI 状态和受控用户动作。

## 考虑过的备选

- **React**：组件生态更大，但本项目不需要其 SSR/服务端组件优势；在无前端存量、个人维护、先建设本地工作台的条件下，Vue 3 的集成与维护成本更低。
- **独立前端仓库**：适合前端团队和发布节奏完全独立的组织；当前一个团队、一份 API 契约和一次端到端交付，同仓更容易防止契约漂移。
- **Next.js**：SSR、SEO 与服务端路由会增加桌面本地工具的部署复杂度，且不能消除长任务、文件和 ComfyUI 的边界问题。

## 后果

- CI 需要增加 Node/pnpm 的 lint、类型、单测、构建与 E2E job，本机命令要与 CI 同源。
- `frontend/` 的 API 类型应从 OpenAPI 生成，不手写第二份接口模型。
- 如果未来个人维护偏好转向 React，迁移成本是整套 UI；这是有意接受的锁定，不应在没有产品证据时中途换框架。
- monorepo 的 CI 时间会上升，应拆 job 并缓存依赖，而不是拆仓库。
