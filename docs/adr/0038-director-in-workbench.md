# 导演台进工作台

> **状态（2026-11-14 复核）**：已接受；随 D8（#253）落地，裁定在 #261–#266 实现，交付归档与最终包比对在 #266 收尾。真实验收按 2026-11-13 用户裁定延后到 Program Overview 全部子 spec 完成之后。

D8 把 CLI 里已经跑通的导演台路线搬进工作台：会话仍在浏览器里从创建走到 `completed`，段视频由用户在 ComfyUI 导演台里生成并回交，系统只做可证层（帧数、段号、包结构），**语义验收留在导演台 UI**。这条路线与 `base`/`ref` 共用同一套会话、任务、人工待办与产物边界，不新造状态机。这里记三件会被后来者反复追问的裁定，以及一处交付闸门的落地取舍。

## 决定

1. **改一段不重打包：初始包是计划，最终包是结论。**
   - 初始包（`director/initial.mmxpack.zip`）在首次打包后**冻结**：用户改段词、在导演台里挂尾帧、调整 UI，都不会触发重建。重建会重置用户在导演台里已经做的映射，把「用户手里的那份包」换成一个他没看过的版本。
   - 差异只在交付时补记：用户导出的最终包与初始包逐段比对（`segments[].id` 为 join 键，`fl2v` 另比 `shots[].prompt`，**不比帧数**——最终包的 `frameCount` 可能被 UI 归一化改过），每个改过的段补一行 `rewrite`（`prompt_before` 取初始包、`prompt_after` 取最终包）。
   - 页面必须明写这句话，否则用户会把「包不是最新的」当成缺陷；这是交互口径，不是提示文案。

2. **语义验收留在导演台 UI，工作台只做可证层。**
   - 工作台判的是帧数、段号、包结构、路径安全这类**机器能证明**的事：段视频用 `companion.judge_video_evidence` 认单段/合并/整片三种导出形态，容差只放「有引导段少 N 帧」；段账只写 `output`/`invalidate` 两类行。
   - 不把 D6 的读图审计搬过来：导演台的「这段画面是否符合剧情」由人在导演台里看，工作台没有 `end_hook` 判据、不调 `describe_image`。搬过来会造出两套相互矛盾的验收口径。
   - 先校验再落盘：交付（`director.delivery.deliver`）在校验完之前一个字节都不写；失败不落半份交付。

3. **段缓存由系统删，不交给用户。**
   - 插件缓存指纹**不含父段身份**：改了第 N 段之后，第 N+1 段按同一缓存名重跑会命中旧产出。所以「换一段」在导演台上是**级联**：作废第 N..末段的通过行（只追加 `invalidate`，不改写旧行）并删掉这些段的 `seg_XXXX.*` 缓存与项目侧派生件（`tailframe-NN.md`、`frame-KK-last.png`）。
   - 删除有两条路径判据：目录级解析后必须仍在配置根内（`_require_cache_inside_root`），逐文件再用 `cache.assert_files_inside` 确认；只留后者时，目录本身被链接出去会让它的基准跟着跑。
   - 与 `ref` 的「只换视频」语义**不同构**：两条路线各按自己的能力判，不合成一个开关。

4. **交付闸门是唯一新增的人工待办（`director_delivery`），复用既有 resolve 端点。**
   - spec §5.6/§14 的待办清单没有列它；不加它就没有任何合法入口把「成片 + 最终包」交回系统，而新增端点会破坏「不新增端点」的约束。落法是：新增待办 kind 与 `decision=submit_delivery`，载荷带两个必填素材 id（成片 mp4 与最终包 zip），事件仍是十种闭集里的 `action_item.created` / `action_item.resolved`。
   - 同步校验（AC 要 422、不归档）：最终包能安全解包、`timeline.json` 段数与计划一致；成片宽高走 `director.aspect_flow.final_film_verdict`（**`deliver` 不查宽高**，漏调就是静默放行）。通过后才起交付 job 做复制、哈希与归档。
   - 这是本 spec 唯一超出 §5.6/§14 字面清单的扩展，理由是不加它时「交付归档」这条 AC 无法被任何请求触发。

## 考虑过的备选

- **改词后重建初始包**：包始终「最新」，但会重置用户在导演台里的尾帧与 UI 改动；用户看到的是自己没做过的版本，且每次改词都要重新导入一遍。放弃。
- **把语义验收也搬进工作台**：能自动化，但与「人在导演台里看画面」的事实冲突，且要引入第二套读图审计与阈值。放弃。
- **段缓存留给用户手删**：插件不会因为父段变了就换缓存键，用户几乎不可能知道要删哪几个文件；留着会让下一段静默复用旧产出。放弃。
- **为交付新增端点**：语义更直白，但破坏「不新增端点」的约束，且素材上传/产物读取/媒体播放的边界要再分一套。放弃，改为复用 resolve 端点。

## 落地时与 D8 spec 字面的偏差

实现按 spec 走，下面五处是落地时**故意**偏离字面；不偏离就没有合法入口，或会把两种语义不同的失败压成一码：

1. **多了一个交付待办 `director_delivery`（`decision=submit_delivery`、job kind `delivery`），§5.6/§14 的待办清单没有列它。** 不加它就没有任何合法入口把「成片 + 最终包」交回系统（决定 4 的完整理由）。
2. **错误码多到 11 个：新增 `director_continuity_invalid`，§15 只列了十个。** 它对应插件 `continuityMode` 的取值非法，与「选错生成模式」（`director_mode_invalid`）语义不同；合成一码会让前端分不清该改哪个字段。
3. **换一段时第 N 段落 `pending`，不是票面写的 `waiting_video`。** 导演台要先重新生成被级联删掉的按需词，词不齐时挂 `segment_video` 会让用户拿着缺失的清单去跑。
4. **级联作废与删缓存从第 N 段起，spec §11.1 字面写第 N+1.. 段。** 第 N 段自己的旧缓存必须删，否则插件按同一缓存名命中旧产出（决定 3 已写理由）。
5. **§11.3「改词补 rewrite 行」只在交付比对时落地。** 工作台没有就地改词入口（spec §2 明确不做），段词全文本来就能在段卡片复制；差异改在交付时由初始包与最终包比对补记。
