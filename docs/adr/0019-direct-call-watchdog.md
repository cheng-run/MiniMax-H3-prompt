# 直调模型的等待看门狗：一个入口，接全仓

2026-10-22 的实测反馈里有三条是同一个病：用户不知道程序在不在跑。

- 素材循环整个不在 `_progress_scope` 里，`[读图校对]` 之后静默调用非流式读图（`timeout=900`），连结束事件都没有订阅者。
- 敲完「下一个出谁」后、打印提示词前，静默跑一次回灌对齐（`align_asset_prompt` 直接 `llm.invoke`）。
- 拆段/写段用同一个流式客户端，但**绕过 `run_agent`**：没有首字节事件、没有重试、没有预算；异常被吞成 `None`，只表现为白等 30 秒后静默降级为机械拆分 / 跳过该段。

根因不是「忘了加 print」，而是**两条调用路径分裂**：`run_agent` 有整套看门狗（首字节线/块间线/预算/事件，ADR 0015），直接 `llm.invoke` 与 `describe_image` 什么也没有。逐处打补丁就是又一次「规则在、接线不在」。

## 决定

1. 建一个**直调等待入口**（同一份首字节心跳、卡住重试、调用预算、面向用户的失败诊断），所有直接 `llm.invoke` 改走它：拆段、写段、回退写段、ref 段改写、素材回灌对齐、素材改写、澄清、摘要、圆桌。
2. 素材循环纳入事件订阅；读图客户端改**流式 + 30 秒首字节线**（网关不支持流式时明确报错并回退到「只报已等时长」）。
3. 长步骤加**步骤横幅**：正在做什么 + 第几轮/N + 已等 Xs（qa 复审、组装、修正、逐段写段都算）。
4. 写段**写一段出一段**：每段落盘即打印该段提示词，不等全部写完。
5. 拆段失败先按看门狗重试，仍失败再回退机械拆分，并打印原因——回退本身是对的，静默才是错的。

## 考虑过的备选

- **只加提示行（「校对中…」）**：不动事件总线的话，900 秒的读图仍然只有一行字，判不出卡住。
- **只接拆段/写段两条**：素材循环的读图与回灌仍在静默，用户反馈的另外两条不修。
- **真 token 流渲染**：结构化输出会被刷屏，且调用方仍拿不到结果边界。
- **拆段失败硬停**：机械拆分是合法退路，硬停只会把一次可恢复的失败变成一次重跑。

## 后果

- 直调路径的 token 目前**不进成本表**；统一入口可顺带记账，成本表数字会因此上升（预期变化，不是回归）。
- 读图改流式后，「卡住」与「慢」第一次可分；但中流断流不重试（与主档同口径，见 ADR 0015）。
- 首字节线只判「有没有数据」，不判「生成得对不对」——它是存活信号，不是质量信号。
- 圆桌与摘要也走同一入口，它们的失败诊断从此与角色调用同形。
