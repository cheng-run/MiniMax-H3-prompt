# 拼接归系统：扩到首尾帧链，裁首帧是结构性接缝的保险

ADR 0014 把「拼接归用户」反转成「拼接归系统」时，适用面写的是多参（ref2va）路线。首尾帧链此时仍是旧形态：全部段验收通过后只打印一句「可在剪辑工具中按顺序拼接 `segments/` 下的各段输出」，就把会话标成完成——「哪几段过了」要用户自己记、N 个视频要自己找、顺序要自己排。2026-10-27 的 spec #92 把同一条纪律扩到首尾帧链：全段通过后由系统接出 `<生成目录>/final.mp4`（issue #96），拼接失败不标完成、重进向导直接续拼（#97），桥接帧恒取末帧、拼接时裁掉第 2..N 段的首帧（#98）。

## 为什么本该是同一件事

三条理由，与 ADR 0014 记的是同一组，只是这一侧更锋利：

1. **纪律必须住在系统里**。spec #54 立的「**未通过即不拼**」只有在系统拼接时才可执行。缺一段的成片时长对不上总时长，是伪产物，比没有更坏；而拼接留在用户手上时，系统连「用户拼了一条缺段的片子」都不会知道。
2. **段序与账本来就在系统手里**。首尾帧链的段序落 `segments/plan.json`（机械回退路径在全部段通过后由 `_write_mechanical_plan` 补写，issue #96），通过与否从 #94 起落 `segments/shot-ledger.jsonl`（视频**绝对路径** + **SHA256**）。两件输入齐了还让用户开剪辑软件按记忆排，就是把一件已可自动化的收尾推回给人。
3. **首尾帧链比多参更经不起排错顺序**。第 N+1 段是以第 N 段的尾帧为第一帧生成的——它不是「另一段素材」，而是链上的一环。用户凭记忆排错，得到的是一条人物乱跳的片子，而且系统不会告诉他排错了。硬接还有第二个问题：两段交界本来就是同一次衔接的两端，原样接起来会重一帧（spec #92 实测四道接缝里三道回退 4 帧 = 0.167s）。

## 段尾落定是主解，裁帧是保险

这两件事解决的不是同一个问题，装配在一起时容易被当成同一件：

- **主解是写作与规划纪律**（issue #95）：分段规划不得在动作中途切开、每段必须声明末态；写段请求带上本段计划的末态声明，并要求动作在本段时长内落定。**目标**是让每一段自己是一个完整的动作单元、结束在一个能接得上的状态。
- **裁帧是保险**：第 N+1 段的第一帧**就是**第 N 段的末帧，这是尾帧接力的**结构性**事实，与两段各写了什么无关。所以哪怕段尾落定做得再好，原样接起来每个接缝都会停一帧。裁掉第 2..N 段的首帧之后，接缝两侧是「段 N 末帧｜段 N+1 第二帧」——画面往前走，而不是停一帧。

**两者不能互相替代**：裁帧治不了「动作没做完时间就到了」（那是内容问题，落定治），落定也治不了结构性重复（那是链的构造，裁帧治）。

**将来想删掉裁帧的人，需要先知道当初为什么加**：2026-09-18 那份产物里，四道接缝合计回退 0.5 秒（占 28.67 秒的 1.7%），**肉眼不可辨**——但那是因为段尾被冻住了（段 3 末四帧彼此只差 0.57，仓库自己的审计记「接缝静止 4.04 秒，占 14.1%」）。「看不见」是冻结的副产品，不是回退本身无害。段尾一旦按 #95 的纪律活起来，同样的回退就会从「看不见的停顿」变成可见的倒带。裁帧正是为了不让「把段尾写活」这件事反过来赔上接缝。

## 桥接帧为什么恒取末帧

#98 之前，桥接帧沿用多参的口径：**最后 5 帧里取最锐利的一帧**。这条口径在首尾帧链上是错的，因为桥接帧在这里不只是「下一段要认得出人物的一张图」，它同时决定了接缝的**时间位置**——取到倒数第几帧，就等于让下一段从「段 N 的倒数第几帧」起步，也就等于决定了该裁几帧。

段尾按新纪律落定时，最后 5 帧的锐度是一条平盘（2026-10-26 实测 100.9 / 100.8 / 100.0 / 99.8 / 101.9），`max()` 等于随机。随机会让「回退了几帧」「成片该裁多少帧」两件事都不可确定，而**成片的帧数必须能被一条算式核对**（各段实测帧数之和减去接缝数；实测样例 688 − 4 = 684 帧）。所以首尾帧链改为**恒取末帧**，锐度从**选帧依据**降级为**质量告警**：末帧低于既有阈值时只打印「本段末可能有运动模糊，下一段识别可能不稳」，照旧用末帧。

**这条改动的作用域必须停在首尾帧链**：`tools/frame_auditor.extract_last_frame` 是多参语义层也在用的共用原语，多参判的是「接近尾部的画面」，挑一张更锐利的邻近帧不改判据。实现因此是加参数（`sharpest: bool = True`，默认值一字未改），而不是改原语语义。

## 为什么不提供换段拼接命令

多参有 `uv run launch.py ref-concat <生成目录> --replace N <新视频>`：重跑某一段之后不必从头走完整流程。首尾帧链**不提供**，这是结构性的，不是还没做：

换掉中间第 N 段，会让第 N+1 段的首帧锚**不再是它的末帧**——第 N+1 段当初就是拿第 N 段的末帧作第一帧生成的。新视频的末帧多半是另一个画面，于是第 N+1 段的开场与它不再连续，第 N+1 段之后整条链的衔接前提全部失效。那等于由系统亲手制造一个新的接缝断裂，而它恰恰是这套收尾要消灭的东西。多参没有这层约束（跨段连续性靠参考素材与文本声明，不靠帧接力），所以那条命令不能照搬。

末段替换仍可做，但走流程内的「重跑末段」：末段没有下游，换它不破坏任何锚。

## 落法

- **共用核心**：段表覆盖判据、SHA256 核对、只报短的时长核对抽进与路线无关的 `final_film.assemble_film`（issue #93）。「未通过即不拼」住在被拼接的那一处，不退化成调用方的 `if`。
- **拼接口径是入参，不是共用件里的分支**：多参 `ConcatStrategy.STREAM_COPY_FIRST`（优先无损 stream-copy，失败转重编码，行为一字未改），首尾帧链 `ConcatStrategy.TRIM_FIRST_FRAME`。抽件时「顺手统一」等于悄悄改变多参的成片行为。
- **画质档 CRF 16**（首尾帧链）：本项目的瓶颈本来就是画质，接缝重编码是这条路线唯一不可避免的一代损失，不给它降档。多参那一档续用历史值 CRF 18——它已交付过产物，改它等于悄悄改变既有产物的画质。
- **单次 filter 图，不落中间文件**：每多一次编码就多损失一代画质；中间文件在失败时还会留在生成目录里，让人分不清哪个才是成片。
- **兜底必须说破**：裁首帧重编码这一路挂掉时退回朴素拼接（`stream-copy-no-trim`），但接缝又保留了重复首帧——结果对象的拼接方式字段必须能辨识这一档，并当面说破。**静默降级**等于用户拿到一条接缝抽帧的成片却以为问题在别处。
- **拼接前核尺寸与帧率一致**：这既是产品判断（不一致说明交回了别的片子的产出），也是 concat filter 的技术前提——ffmpeg 不会替人拦，它会按第一段的尺寸硬接，或接出一条时长悄悄不对的片子，全程不报错。
- **≤10 秒不分段的短视频不出成片**：那条视频本来就是一次生成的结果，没有可拼的东西。这条不对称在 `CONTEXT.md` 的**成片**词条里说破。

## 被否决的方案

1. **只靠段尾落定、不裁帧**：结构性重复与内容无关，落定做得再好，每个接缝仍会停一帧；而裁帧是唯一能在不改段视频的前提下消掉它的手段。
2. **只裁帧、不要求段尾落定**：裁帧只能消掉重复的那一帧，治不了「动作没做完时间就到了」——那种段自己就不完整，接上去是另一个毛病。
3. **桥接帧继续按「最后五帧最锐利」选**：段尾落定后锐度是平盘，等于随机；随机让「该裁几帧」不可确定，而帧数算式是这条票的确定性验收判据。
4. **在首尾帧链上也提供 `--replace`**：等于允许用户亲手打断下一段的首帧锚，与「接缝不重、链条连续」的目标正面冲突。多参能提供是因为它没有帧接力。
5. **靠用户在剪辑软件里手工拼**（#39 ID13 的原形态，也是首尾帧链此前的收尾）：见「为什么本该是同一件事」三条。
