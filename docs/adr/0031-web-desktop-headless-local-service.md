# Web 与桌面共用本地 Headless Service

> **状态（2026-11-09 复核）**：已接受；桌面外壳的具体实现留给交付规格，不在此处锁死。

长视频生成包含多次模型调用、素材读取、人工判断、分段陪跑和本地 ComfyUI 交互。浏览器不能直接承担这些本机能力，而把业务逻辑嵌进桌面外壳又会让 Web MVP 与 EXE 分叉。因此，两种产品形态都通过同一个本地服务访问同一个生成内核。

## 决定

1. Python 核心先抽成可脱离终端向导验收的 Headless Service；生成会话、执行任务和人工待办由服务端拥有状态机。
2. 浏览器与桌面外壳均加载同一套前端；桌面窗口只负责生命周期和原生能力桥接，不重写业务页面。
3. 控制接口使用版本化 REST，长任务进度和人工待办通过 SSE 推送；前端动作通过受控 action 提交，不直接修改内部状态。
4. 图片和视频以资产标识传输和引用；上传使用流式 multipart，播放使用支持 Range 的媒体响应。前端不持有任意本地路径。
5. 本地服务只绑定 `127.0.0.1`，使用启动令牌或同源会话保护，并把 API 密钥留在 Python 侧。

## 考虑过的备选

- **原生 Qt 桌面重写**：本地能力最直接，但复杂的时间线、视频预览和表单开发成本高，而且会复制 Web MVP 的产品逻辑。
- **终端向导直接包成 EXE**：交付快，却不能改善多阶段工作台的产品体验，也无法复用浏览器组件。
- **WebSocket**：适合双向高频实时协作；本项目主要是客户端动作与服务端进度的单向推送，SSE 的断线恢复与事件续传更简单。
- **GraphQL 或 gRPC**：对本地单用户 CRUD、文件流和任务事件没有必要，反而增加浏览器与打包复杂度。

## 后果

- 必须把约 6,265 行的终端向导逐步抽成服务、任务和资产边界，不能让前端依赖终端交互顺序。
- 任务启动返回 `job_id`，HTTP 请求不得等待完整 LLM 管线结束；人工节点应持久化为等待状态，而不是阻塞线程。
- 会话写入需要单写入者、原子落盘和恢复语义，避免前端、Worker 与终端同时覆盖状态。
- 桌面封装要处理端口、进程退出、WebView、大文件、日志和打包资源；这些是交付规格的验收项。
- 未来若做多人远程产品，应增加身份、租户、TLS 和对象存储，而不是把当前本机服务直接暴露到公网。
