# 工作台媒体读取与本地鉴权

> **状态（2026-11-10 复核）**：已接受；本地鉴权（§4）随 D3-1（#223）落地，媒体读取的 Range 与路径白名单随 D3-3 实现。
> **状态追加（2026-11-10，D3-4 / #226 验收）**：在真实浏览器与真实素材上复验通过（Playwright 上传 + `<video>` seek 出现 206；真实照片上传、真实 `final.mp4` 播放与 Range 字节核对），据此定稿。

D2 把 `base` 的生命周期搬到了服务端，但明写鉴权、Origin/Host 校验与启动令牌「是 D3 的事」，并且是有意留的空窗期（#214 §12）。补上之后，工作台要能接收用户素材、播放会话产出的媒体，而**只有本机同源页面能用它**。这两件事共用同一套入口守门与同一套路径白名单，所以放在一份 ADR 里定。

## 决定

1. **三层守门**：只绑回环（`api/__main__.py` 的 `HOST=127.0.0.1`）、Host/Origin 白名单、启动令牌。前两层对所有请求生效，第三层只对 `/api/*` 的非豁免面生效。
2. **Host 与 Origin 只看主机名，端口不限**。允许集合固定为 `127.0.0.1` / `localhost` / `[::1]`。端口不限不是宽松，是硬要求：开发期 Vite 代理 `changeOrigin: false`，浏览器过来的 `Host` 是 `localhost:5173`；把端口也钉死就必须维护两份配置，而两份配置迟早会分叉。
3. **每进程随机启动令牌**：32 字节 URL-safe 随机串，只存内存，重启即换。`GET /api/v1/auth/token` 返回它**并**下发 `wb_session` Cookie（`SameSite=Strict`、`HttpOnly`、`Path=/api/v1`、无 `Max-Age`）。两个值相同、来源相同。
4. **凭据二选一：请求头 `X-Workbench-Token` 或 Cookie**。`<video src>` / `<img src>` 由浏览器自己发请求，挂不上自定义请求头，也包不了 `fetch`；媒体端点若只认头就永远 401。前端 `fetch` 与 SSE 走请求头，媒体元素靠 Cookie。
5. **豁免面是闭合的三处**：`GET /api/v1/health`、`GET /api/v1/auth/token`（这两条只豁免 GET/HEAD——其它方法仍要凭据，否则 401 与 405 的差别会泄露路由存在）、静态资源与 SPA 兜底（含 `/openapi.json`、`/docs`）。不在 `/api` 下的一律豁免；未知 `/api/*` 仍然要凭据。
6. **令牌挡的是跨站页面，不是本机进程。** 引导端点不设防是有意的：服务不设 CORS，跨站页面读不到响应体，`SameSite=Strict` 也让它们拿不到 Cookie；本机进程能拿到，但它们本来就能直接读写 `output/sessions/`，不在威胁模型内。不要把这里当通用认证或多用户方案。
7. **令牌不进 URL、不进 access log、不进错误体、不进验收证据。** 请求头天然不进 access log；验收驱动器取令牌时**不记录响应体**——证据目录会被随手拷走。
8. **媒体只服务会话登记根**（`sessions_root`）：素材与产物都先 `resolve()` 再判 `relative_to(root)`；`asset_id` 拆出的会话标识必须已通过存储层解析，文件名必须是 `<16 位十六进制>.<已知扩展名>`。**不接** `D:\素材库`，也**不直服** ComfyUI 输出目录——「把外部目录挂成媒体根」等于放开任意路径读。
9. **Range 只支持单段**（`bytes=a-b` / `a-` / `-n`），越界、语法非法与多段一律 416；`final.mp4` 与素材共用同一套解析。浏览器 `<video>` 的播放与拖动只用单段，multipart/byteranges 是没有消费者的复杂度。

## 考虑过的备选

- **`CORSMiddleware` + 允许来源清单**：CORS 是「允许谁读响应」的声明，不是拒绝机制；不设 CORS 时跨站页面本来就拿不到响应体。再叠一份来源清单，只会多一处与 Host 校验重复且更容易写错的口径。
- **`TrustedHostMiddleware`**：只查 Host，不支持我们需要的「端口不限 + 按主机名判」的语义，也不处理 Origin 与凭据。与其绕开它的限制，不如写一层能同时表达三层判定的中间件。
- **把令牌放进 URL 查询参数**：媒体元素确实能用，但 URL 会进 access log、Referer 与浏览器历史——等于把凭据写进证据。Cookie + `SameSite=Strict` 达到同一目的而不留痕。
- **CSRF token / 双提交 Cookie**：本服务不设跨站写入口（SameSite=Strict 已经挡住跨站请求带凭据），再加一层只是给本机用户加仪式。
- **只做 Host 校验、不发令牌**：挡不住「本机其它网页」——同源策略按 origin 算，`localhost:5173` 上的任意脚本都能读 `127.0.0.1:8000` 的响应；令牌让「谁先拿到引导端点」变成唯一的门。
- **Unix domain socket / 命名管道**：浏览器用不了，且会把「本机」与「浏览器」两种调用方分叉成两套安全模型。

## 后果

- 前端所有 API 调用必须先取令牌（模块内缓存一次）；服务重启后旧令牌失效，而缓存里还是旧值——客户端不做 401 自动续取，刷新页面即可恢复。媒体元素依赖引导端点顺带写入的 Cookie，所以 `main.ts` 在页面启动时主动取一次——`<video>` 不必等页面上先发生别的 API 调用。
- 开发期与生产期走同一套规则：Vite 代理不换 Host 也能过，因为只看主机名。
- 本机进程（curl、脚本、验收驱动器）必须自己取令牌；验收证据里不许出现令牌。
- `sessions_root` 成为媒体读取的唯一边界；将来要接素材库或 ComfyUI 输出，必须另立「登记根」抽象，不能在端点上直接拼外部路径。
- 令牌是进程级而非会话级：多标签页共享同一凭证；这是单用户本机服务的合理简化，将来若做多用户必须换掉。
