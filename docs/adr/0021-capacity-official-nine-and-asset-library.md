# 容量以官方 9 张为准，素材进长期素材库

2026-10-25 的 spec #84 定案：多参路线的参考素材容量改为**官方 API 的单次请求上限**（≤9 图 + ≤3 视频 + ≤3 音频、总文件 ≤12），交回的素材进**长期素材库**，每个执行段只取本段用到的 ≤9 张；登记工作流回到 **9 图槽 V2**，2026-10-22 建起的 **24 槽 V3 与 Refs24 节点包从仓库退役**（本机件保留）。本记录写下这组口径、支撑它的两组独立证据，以及被否决的备选。

票号：spec #84；子票 #85（素材库）、#86（容量）、#87/#88（模型纪律）、#89（分镜表）、#90（退役）、#91（文档收口）。

## 决定

1. **容量口径取自官方 API，不取自本仓节点槽数。** 单次请求 ≤9 图 / ≤3 视频 / ≤3 音频，且总文件 ≤12。四条同时成立：9 图 + 3 视频已经用满 12 个文件，独立音频没有位置；「9 图 + 1 视频 + 3 音频」是 13 个文件，在请求层根本不成立。
2. **按「一次请求」判，不按整片库存判。** 9 图上限落在**每个执行段**的接线卡；整片台账层只判视频/音频（它们没有段内子集，每次请求全带上，该层的总文件预算随之只数视频与音频）；≤15 秒直出整片即一次请求，按图/视频/音频/总文件全判。超限**报错并点名**具体素材，不截断、不自动丢弃——截掉的素材会在正文里变成悬空的 `<Picture N>`，自动丢弃则是替用户删了他交回的素材。
3. **登记工作流回到 V2（9 图槽）**；24 槽 V3 工作流与 Refs24 节点包的**仓库副本**退役（issue #90）。本机节点包与 V3 工作流保留（其他项目可能还在用），但它们不再是登记路径，也不构成容量口径。
4. **素材进长期素材库。** 库根进配置（默认 `D:\素材库`，必须绝对路径）；一次运行一个子目录（主题摘要 + 短哈希命名，防不同主题撞名；同一主题重跑追加 `-2`、不复用）；文件按 `[Video|Audio ]<编号>-<语义名>` 命名；换版追加 `-r2`、旧文件保留。生成目录**不再保存图片副本**；台账记库根 + 相对路径，读图校对、SHA 校验、接线与段内取用经**同一个解析口**取文件。没有库根字段的旧台账按旧布局读，不迁移。
5. **生图提示词按模型分纪律块**（issue #87/#88）：一份模板、一个 JSON 契约，按目标模型追加对应纪律块（Z-Image 中文短句全正向 / Qwen-Image 英文长文不写负面 / MOSS-Image 英文并填负面标签）。换模型必须同时换纪律——拿错一块不会报错，只会让词按另一家的写法写、质量掉一档。Qwen-Image 2.1 是 Qwen Research License，**仅限非商用**，商用前切档。
6. **多参有专属四列分镜表**（issue #89）：一行一个**执行段**（不是 `[Shot N]`），内容与段内素材子集同源；只由多参路线产出，base 的整片镜头清单不动。
7. **路线隔离不变**：唯一判据仍是生成路线，base 路线代码路径零修改，验收含逐字节对照（ADR 0020）。

术语定义见 `CONTEXT.md` 的**素材库**、**素材库子目录**、**模型纪律块**、**多参分镜表**、**9 张上限**。

## 为什么：两组独立证据落在同一个数上

**官方契约。** 官方 API 的单次请求规范写明 ≤9 图 + ≤3 视频 + ≤3 音频、总文件 ≤12、prompt ≤7000 字符、请求体 ≤64 MB（spec #84「事实底账」，来源 minimax.io v2-create 文档）。这是外部契约，不是本仓的保守估计。

**本机实测。** 2026-10-22 的一次真实多参运行（06:22–06:28）在 24 张参考图上 OOM：Qwen3-VL 的编码序列被撑到约 **5.4 万 token**，注意力计算要一次性分配 **232.03 GiB**，16GB 卡上换任何注意力后端都救不回来——朴素路径照样整块分配。同一台机器上 9 张以内此前实测通过。也就是说「超了会怎样」不是变慢，而是**跑不出来**，校验必须发生在提交之前、在仓库这一侧。现场记录见 spec #84「事实底账」；仓库未保留该次运行的日志副本，这些数字无法在本仓重放，复现需 16GB 卡 + 24 张参考图。

**素材没有长期落点。** 交回素材原先复制进 `<生成目录>/assets/`，图与提示词产物混在一次性目录里；换一个 GEN 就找不到上一版素材。素材库把「一次运行的产物」与「跨运行复用的素材」分开，台账用库根 + 相对路径 + SHA256 保持可复测。

ADR 0017 的排查结论仍然保留：模型侧 `minimax_refs` 接受任意长度，9 是节点 UI 上限**同时**也是官方请求上限——两处数值相同、性质不同。本记录不重复那次排查，只把它接到容量口径上：**仓库执行的是请求契约的 9，不是节点端口的 9**。

## 被否决的方案

**把 24 槽当默认容量路径（ADR 0017 的原决定）。** 被 2026-10-22 的 OOM 实测证否：扩槽从一开始就不该成为默认路径。ADR 0017 的状态行按「只追加、不覆写」更正，正文保留当时的推理，见该文末「2026-10-25 处置」。

**只做按段调度、不扩槽。** ADR 0017 当时以「用户这几天仍然跑不了」为由否决，先做 P1 全喂。实测证明 24 张全喂根本跑不出来，先跑通的那条路本身不成立——按段取用反而是唯一可行路线。

**用整片库存判 9 图。** 复审时抓到的口径错误：拿整片 24 张素材去判「≤9」，会把一个合法的多段长片整片拦死，正好废掉「按段取用」。判据必须挂在**这一次请求**上，而不是整片台账。

**复用同名素材库子目录。** 重跑沿用旧目录，上一轮的图会**静默冒充**本轮的交回物，而屏幕与产物都看不出「哪张图是这轮放进来的」。与「复用 GEN 会吞掉追加式账」是同族病。新运行另开 `-2`。

**生成目录当素材库。** 一次性目录，GEN 一换就丢——这正是要修的原始问题。

**两处都存（生成目录 + 素材库）。** 双真源，换版时两份会不一致，且没有任何一处能说自己是权威。

**设计阶段限量到 9。** 等于让设计迁就接线，而 24 张是剧本实际需要；否掉后改用按段取用，让设计量不受接线容量约束。

**用 `SceneDispatcher2` 按名字选图。** 它的名字匹配是模糊匹配（互为子串/切词交集），会静默串图；段内子集由分段规划显式定案并落 `assets_in_segment`。

**三份完整提示词模板（一模型一份）。** 三份全文会各自漂移；改一份公共契约时要改三处，漏一处就是静默掉一档。故取「一份模板 + 按模型替换的纪律块」，三档共用同一个 JSON 契约与锁死清单规则。

**复用整片镜头清单 / 官方六列镜头表。** 官方六列（Hook、逐秒指令）是 3D 动画技能口径，与 4–15 秒执行段不对齐；而仓库只有执行段这一层带起始态、段尾钩子、摘要与段内素材子集，按单个镜头分行就得拿段级声明冒充镜头级声明。故多参分镜表一行一个执行段、四列。

**把 9 当作模型能力上限。** 模型侧接受任意长度（ADR 0017 排查结论）；9 是请求契约。写反了会导致「模型不行」的错误归因，掩盖真正该做的是按段取用。

## 后果

- **24 张素材的片子仍然能跑**：素材库整片可以超过 9 张，只要每个执行段取 ≤9 张。整片台账不再判图数，图数由每段接线卡与直出路径判。
- **四个上限是外部契约**：改动任何一个数都要同时改票面与本记录，不能当成调参。
- **素材库在仓外、跨运行存在**：撤下素材只撤登记、不删库内文件；换版保留旧文件，旧产物仍可复测。已有 GEN 目录按旧布局原样读，不迁移。
- **仓库不再有 V3/Refs24 副本**：少了一份「跟本机版漂移」的维护负担，代价是仓库里没有对应的本地回退件——本机件仍在，但不再是登记路径。
- **base 路线逐字节不变**：共享函数只允许「非多参路线直接返回原行为」形态的守卫；新增产物出口必须走同一条路线入口（ADR 0020）。
- **24 槽里唯一存活的想法是按段调度**：扩槽退役，按段取用成为主线。
