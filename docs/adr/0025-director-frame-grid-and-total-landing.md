# 导演台段长按 17k+5 落位，总长取最近可达值

日期：2026-10-29。关系：细化并**修正** `docs/adr/0024-director-route-native-semantics.md` 的第 6 条（「总时长在规划期精确落位：段1 声明 108、段2–5 各 141，合计 720」）。票 #102（段规划）实现前，用户裁定：**网格优先，接受总长差 1 帧**。

## 背景：720 帧在真实插件契约下不可达

制作 spec 时按「声明帧 108（无引导）+ 141×4（有引导）」推出了 720。插件源码复核后，这条算例不成立：

1. **声明帧由 `durationSec` 决定**。后端 `_segment_frame_count` 对 `t2v/i2v/r2v/fl2v/mixed` **优先读 `durationSec`**，按 `align(round(秒×24))` 重算并吸附到 `17k+5`（`ComfyUI_MiniMaxH3_Director/director/gen_timeline.py:80-99`）；只有省略 `durationSec` 才回落到 `frameCount`。
2. **导出帧的余数由段类型决定**。有引导段导出 = `align(声明)+12`，恒为 17 的倍数；无引导段导出 = 声明，恒为 `17k+5`（ADR 0024 的算术本身成立）。
3. **因此 n 段的总导出帧恒 ≡ 5×无引导段数 (mod 17)**。5 段能取到的余数是 `{0, 5, 10, 15, 3, 8}`；`720 ≡ 6 (mod 17)`，**永远取不到**。最近的可达值是 719（1 个无引导段）与 736（1 个无引导段、声明 124）。
4. 若靠「省略 `durationSec`、只写 `frameCount=108`」硬凑 720：后端会照 108 用，但 UI 一旦编辑该段帧数/帧率，`preferredDurationSecFromFrames(108)` 找不到反演秒数，回落 4.5s，随即被吸附成 124——总长**静默变 736**；`fl2v` 模式的 UI 只认 `durationSec`，更脆。

## 决定

1. **每个段的声明帧必须落在 `17k+5` 上**，包内 `durationSec` 与声明帧**严格自洽**（例：107 帧 ↔ 4.0s；141 帧 ↔ 5.8s），不省略、不写不一致的值。
2. **总长取最近可达值**：规划器给定目标秒数后，按「每段都在网格上」枚举可用总量，取与 `目标×24` 差最小者；30 秒片 → **719 帧（29.958s）**，出站清单写明「目标 720、实际落位 719、差 1 帧」。
3. 票 #102 的 AC「导出帧合计 = 720」按本 ADR 解释为「**与 720 最接近的合法落位**」，并在出站说明偏差；测试断言 719，不是 720。
4. 偏差只在**规划期**吃掉（选最近可达值），不在事后裁剪/补帧。

## 后果

- **两套坐标**：规划与可证层用**成片坐标**（导出帧累加，30 秒例为 719）；导演台 `timeline.totalFrames` 与段 `start/length` 用**声明坐标**（声明帧累加，同例为 107 + 4×141 = 671）。差值是 `12×有引导段数`，插件文案本身就写「保完整成片会略长于时间轴」。包构建必须换算，不能把 719 直接写进 `timeline.totalFrames`。
- 「成片总长精确等于 30 秒」在 24fps + 17k 网格下**不可能精确**：可达总量与目标之间最大差 8 帧（约 1/3 秒）。出站必须说明，不能让用户以为出错。
- 规划器的确定性层要能**枚举**合法落位，而不是只做一次四舍五入——「先均分再凑」会落到不可达的余数上。
- 段数由规划 LLM 提议；段数变化会改变可达总量集合，重排逻辑必须按**段类型（有/无引导）**统计，不能按段号硬编码。
- 用户若在导演台里手动改某段秒数，UI 会按同一网格重算，总长随之变化；项目侧不承诺事后追踪这一改动（最终包比对只比提示词，不比帧数）。

## 被否决的备选

- **省略 `durationSec` 保 720**：UI 一编辑就静默变 736，且 fl2v 模式下不可靠（见上）。
- **关闭「保完整」凑 720**：5 段总量恒 ≡ 8 (mod 17) 与引导开关无关，720 仍不可达。
- **改段数凑 720**：需要 8 段且**全部无引导**（放弃这条路线存在的理由），或大量非网格声明帧。
- **事后裁剪/补帧到 720**：违反「不在事后补偿」，且补帧会制造重复帧接缝。
