# H3 生成台账与审计 — 设计

- **日期**：2026-09-20
- **状态**：待审
- **范围**：新增 4 个工具模块 + 一个 CLI 子命令组；不改动现有管线代码

---

## 0. 背景

### 现状

创作链已完成（一句话 → 剧本 → 分段 → 五变体提示词）。执行链**全靠手工**：

```
① 提示词 → 生图（Z-Image / Flux2）      ← 手工
② 挑首尾帧 → 绑到 H3 工作流输入槽        ← 手工
③ 提交 H3 → 生成一段 4–10s 视频（约 10 分钟/段）← 手工
④ N 段 mp4 → 合并成长视频                ← 手工（且尚无代码）
```

手工是**刻意的质量闸门**，不是欠债——在视频质量未达标前不上自动化。这个判断保留。

### 触发事件

2026-09-20 做了一次拼接诊断，把 `MiniMax-H3视频_00003` 误认为真实镜头，据此报出
「接缝硬跳切 66.98」「桥接帧错位」两个错误结论。实际 `00003` 是镜头 3 的**废弃初版**。

根因不是疏忽，而是**磁盘上无法还原「哪个镜头用了哪张帧」**：

| 缺什么 | 后果 |
|---|---|
| 桥接帧文件与视频编号的显式映射 | 只能靠文件名猜 |
| 废弃版本的标记 | 废片与成品混在同一目录 |
| 中断的记录 | 说不出"为什么少了一段" |

### 第二个事实

`plan.json` 期望 6 段，实际只有 5 个镜头——**阿里云百炼免费额度（100 万 token）在第 6 段耗尽，流程中断**。
磁盘上同样看不出这个原因，只有 `progress.json` 的 `done: 5 / total: 6` 一个孤零零的数字。

### 结论

项目缺的不是自动化，是**可追溯性**。在手工搬运仍将持续的前提下，需要让每次生成留下可复查的痕迹。

## 1. 目标与非目标

### 目标

1. **自动重建链路**：从磁盘推断出「镜头 → 视频 → 输入帧」，不依赖任何人工登记
2. **提交前校验**：输入合法性 + 资源可用性
3. **量化接缝**：产出与基线可对比的数字

### 非目标（明确不做）

| 不做 | 原因 |
|---|---|
| 驱动 ComfyUI / 自动提交 | 质量未验证前不自动化；且本项目真正的瓶颈是测量，不是生成速度 |
| 视频合并 | 已实测 0/4 接缝有重复帧，`ffmpeg concat` 即可，随时可加 |
| 改动 `graph/` `ui/` `pipeline.py` `session_store.py` | 风险高收益低；本设计零侵入 |
| 引入 guardrails / deepeval / promptfoo | 只需它们的**语义**，不需要依赖 |
| LLM-as-judge | 本项目有确定性判据（逐帧像素差），无需花钱、无需忍受 flaky |

## 2. 架构与模块划分

**一个数据源 + 三个消费者。**

```
                    ┌──────────────────────────┐
                    │  tools/frame_match.py    │  帧读取与比对原语
                    │  · 中文路径安全读图       │  （cv2 的坑关在这里）
                    │  · 灰度降采样 / MAD 窗口  │
                    └────────────┬─────────────┘
                                 │
        ┌────────────────────────┼────────────────────────┐
        ▼                        ▼                        ▼
┌───────────────┐      ┌─────────────────┐      ┌──────────────────┐
│ tools/        │      │ tools/          │      │ tools/           │
│   ledger.py   │      │   preflight.py  │      │   seam_audit.py  │
│  重建链路     │      │  提交前校验     │      │  拼接 + 量化接缝 │
└───────┬───────┘      └────────┬────────┘      └────────┬─────────┘
        │                       │                        │
        │  产出 ledger.json     │ 读它：上一段是哪段     │ 读它：镜头顺序
        └───────────────────────┴────────────────────────┘
                    ledger.json 是唯一真相源
```

### 模块职责与接口

| 文件 | 职责 | 对外接口（小接口、大实现） |
|---|---|---|
| `tools/frame_match.py` | 帧读取与比对原语 | `imread_unicode(p)` / `read_head_tail(video, k)` / `mad(a, b)` / `match_video(frame, videos, *, window: "head"\|"tail") -> (video, mad)` |
| `tools/ledger.py` | 从磁盘重建链路 | `rebuild(session_dir, output_dirs, *, threshold) -> Ledger` |
| `tools/preflight.py` | 提交前校验 | `check(shot, input_frame, prev_video, prompt, *, budget) -> list[Issue]` |
| `tools/seam_audit.py` | 接缝审计 | `audit(ledger, out_dir, *, baseline=None) -> SeamReport` |

**关键边界**：`preflight` 和 `seam_audit` **不自己推断链路**，只读 `ledger` 的结果。
推断逻辑只有一处，改一次全部受益。

### 落盘位置

```
output/sessions/<主题>-<hash>/GEN001/
├── session-state.json
├── frames/first.png
├── bridge_frames/shot-0N-start.png
├── segments/
│   ├── plan.json
│   ├── progress.json
│   └── shot-0N.md
├── ledger.json              ← 工具生成，每次重扫覆盖
├── ledger.override.json     ← 人写，工具永不覆盖
└── audit/
    ├── baseline.json        ← 人工提升的基线
    ├── <ts>.json            ← 本次原始数据
    └── <ts>.md              ← 人看的报告
```

**ComfyUI 的 output 目录只读，绝不写入**（沿用 `task_package.py` 已立的原则）。

```jsonc
  "warnings": []

```

### 三个设计决定

**① `kind` 靠尺寸判定，不靠猜**

| 尺寸 | 判定 | 依据 |
|---|---|---|
| 1280×736 | `extracted`（视频抽帧） | 与所有 H3 输出同尺寸 |
| 其他（如 3840×2160） | `generated`（生图） | `frames/first.png` 实测为 3840×2160 |

**② `confidence` 三档，且必须配 `evidence`**

`high` / `medium` / `low`。**没有 evidence 的 confidence 无效。** 工具不能让读者无法复查判断依据。

**③ 逃生舱是独立文件**

`ledger.override.json` 由人写，工具永不覆盖。合并顺序：

```
磁盘推断  →  应用 override  →  产出 ledger.json
```

理由：人写的内容与生成的内容若混在同一文件，重扫会把手工修正冲掉。**手写的那份必须活着。**

```jsonc
// ledger.override.json —— 只在推断不出来时写
{
  "shots": { "3": { "video": "MiniMax-H3视频_00007-audio.mp4", "note": "重跑后的成品" } },
  "discarded": { "00004": "被 00007 取代" }
}
```

### 废片判定规则

| 证据 | 强度 |
|---|---|
| 视频**未被任何桥接帧引用**（且不在链上） | 必要条件 |
| 另一个**链上**视频与它首帧几乎相同（mad < `MAD_SAME`），说明两者用了同一张输入图 | → `high`（`00003` 的情形，mad=0.88） |
| 未被引用，但找不到相似的链上视频 | → `medium`，并进 `review_needed` |

> **为什么没有"生成时间最新 → 判定为最后一段"这条特例**：链路正常时，最后一段是某张桥接帧的消费者，**本来就在链上**，不会落进"未被引用"里。链断掉时又无法可靠区分"未完成"与"废弃"，所以一律进 `review_needed` 交给人判断——不猜。

## 4. 推断算法

### 核心：建边，而非猜身份

对每张桥接帧 `B`：

```
src(B) = argmin over 所有视频 v   mad( B, v 的尾窗口 )
dst(B) = argmin over 所有视频 v   mad( B, v 的首窗口 )

边：  src(B) ──── B ────▶ dst(B)
```

### 消歧：三条规则，按优先级

实测暴露了真实歧义——`00003` 与 `00004` 的首帧**都对得上 `shot-03-start.png`**（同一输入图的两次生成，mad=0.88）。

| 优先级 | 规则 | 实际效果 |
|---|---|---|
| **1. 链延续性** | 候选里，**谁的尾帧还被别的桥接帧引用**就选谁 | `00004` 被 `shot-04-start` 引用 → 选它；`00003` 是死胡同 |
| **2. 生成时间** | 同分时取更晚的 | 00004 @12:14 晚于 00003 |
| **3. 命名自洽** | `shot-0N-start.png` 必须落在镜头 N 的输入上 | 交叉校验，见下 |

优先级 1 是主力——它把"哪个是成品"变成图论问题，而不是靠猜。

### 免费自检：命名交叉校验

| 结果 | 处置 |
|---|---|
| 满足 | 互相印证 → `confidence: high` |
| 不满足 | 推断或命名有一处错 → warning + `review_needed` |

### 阈值分级（窗口比对，非单帧）

尾部/头部各取 5 帧取**最小** mad——防止抽帧脚本抽的不是精确最后一帧。

| mad | 判定 | 实测分布 |
|---|---|---|
| < 2 | 同源 → `high` | 0.00 / 0.37 / 0.49 / 1.97 |
| 2 – 5 | 疑似同源 → `medium` | — |
| > 5 | 不同源 | 22 – 67 |

中间隔一个数量级，阈值取哪都安全。可配 `--threshold`，写进 `scan.threshold_mad`。

### 放弃条件：五条硬约束

一律进 `review_needed`，**不猜**：

1. 一张桥接帧找不到 mad < 5 的 `src` 或 `dst`
2. 同一个 `dst` 被两张以上桥接帧指向（链分叉）
3. 链走不到结尾（有视频既没被引用、又不满足"最后一段"条件）
4. 存在视频既不在链上、又无法解释为废片
5. **视频数与 `plan.json` 分段数对不上** → 记为 `interruptions`，并显式报出差异

## 5. 预检规则与失败处置

### A. 可证规则 → `error`，阻断

| 检查 | 判据 |
|---|---|
| 桥接帧文件存在 | 文件在 |
| **桥接帧确实来自上一段尾帧** | `mad(帧, 上一段尾窗口) < 5` |
| 桥接帧尺寸正确 | `== 1280×736` |
| 上一段是成品不是废片 | 查 `ledger.discarded` |
| 段时长在 H3 档位内 | 4–10 秒整数（复用项目已有校验） |

都是**能算出来的事实** → 错了就阻断，别浪费 10 分钟。

### B. 启发式规则 → `warn`，不阻断

| 检查 | 判据 |
|---|---|
| 冻结词 | grep `停住\|定格\|静止\|不动\|不再变化\|停在` |
| 画面连贯性 | `mad(本段规划首帧, 上一段实际尾帧)`（拿得到时） |

**为什么只能是 warn**——实测反证：

| 镜头 | `end_hook` 冻结词 | 末尾静止 |
|---|---|---|
| 1 | "双手**停在**…" | 11 |
| 3 | "镜头**停在**掌心尺度" | 29 |
| **5** | "…对峙**定格**" | **0** |

**镜头 5 有"定格"却没冻。** 冻结词是启发式，不是因果。命中时给出**确定性改写建议**
（如"双手停在书封上" → "双手刚落在书封上"），但需人工确认后才改。

### C. 资源规则 → `refrain`（劝阻，由人决定）

| 检查 | 判据 |
|---|---|
| 剩余额度够不够跑完 | `每段实测均值 × 剩余段数 > 剩余额度` |
| 还能跑几段 | 直接报数：**"按当前消耗，还能跑 7 段"** |

`TokenMeter`（`observability.py`）已按角色累计 token 与成本，但只在跑完后汇总。
增加**运行中检查点**：每完成一段比一次，接近见底时 `reporter.emit` 警告事件
（UI 已订阅事件总线）。

**价值**：把"跑到第 6 段才发现没余额"变成"第 4 段就收到『还能跑 2 段』"。

### 失败处置：映射 guardrails 的语义（不引入依赖）

| 规则类型 | 处置 | 理由 |
|---|---|---|
| 可证规则失败 | `EXCEPTION` | 输入错了 → 先修再提交 |
| 启发式命中 | `NOOP` + 建议 | 可能误报（镜头 5 是反例） |
| 资源不足 | `REFRAIN` | 劝阻，但人可能就想先跑一段 |

### 硬要求：预检必须能独立命令行运行

```
h3 preflight --shot 6 \
             --input-frame output/sessions/<...>/GEN001/bridge_frames/shot-06-start.png \
             --prev-video "D:/Comfyui/ComfyUI/output/视频/MiniMax-H3/2026-09-18/MiniMax-H3视频_00006-audio.mp4"
```

**手工模式下也能用。** 搬去 ComfyUI 之前跑一次，就知道"这张帧对不上"或"额度不够"。
**不需要自动化即可拿到大部分价值。**

## 6. 审计输出

`seam_audit` 不再硬编码镜头顺序，改为**从 `ledger` 读**。

```jsonc
// audit/baseline.json —— 人工提升，不被自动覆盖
{
  "label": "修复前 @2026-09-18",
  "shots": 5, "duration_s": 28.67,
  "seam_still_frames": 97, "seam_still_seconds": 4.04, "seam_still_ratio": 0.141,
  "per_seam_avg_frames": 24.3,
  "per_shot_trailing": [11, 19, 29, 21, 0]
}
```

报告给出对比表：

| 指标 | 基线 | 本次 | 变化 |
|---|---|---|---|
| 接缝静止 · **每缝均值** | 24.3 帧 | ? | ? |
| 接缝静止 · **占全片比例** | 14.1% | ? | ? |
| 镜头 N 末尾静止 | … | ? | ? |

### 比较陷阱（必须处理）

**总数不能跨镜头数比较。** 基线 5 镜头 / 4 道缝，新片若 6 镜头 / 5 道缝，
`97` 与 `120` 比大小毫无意义。

报告**主推「每缝均值」与「占全片比例」**，总数仅作参考并显式标注镜头数。

### 自检先行

先验证**素材本身是好的**：若某段整段 mad 中位数接近 0，那不是"接缝有问题"，
而是**这段视频本身有问题**。先自检再下结论，否则会对着坏素材调半天提示词。

## 7. 错误处理：三条铁律

**① 只读。** 预检、台账、审计**绝不修改任何输入文件**。

**② 绝不静默失败。** 本项目现有约 10 处 `except Exception: pass`。新代码**一个都不许有**。
宁可报告里多一行"这 3 个文件读不了"，也不要让结果看起来是完整的。

**③ 部分失败显式记录，而非整体崩。**

| 情况 | 处置 |
|---|---|
| 会话目录 / `plan.json` 缺失 | 报错退出（无法推断） |
| 某个视频读不了 | 跳过 + warning，其余继续 |
| 某张桥接帧读不了 | 该接缝进 `review_needed` |
| `ledger.json` 版本不认识 | **拒读**并提示，不猜 |
| ComfyUI output 目录不存在 | 报错退出 |

## 8. 测试策略

### 层 1：合成 fixture（进 CI，秒级）

用 numpy 造：3 段合成视频（纯色背景 + 移动方块，尾帧可预测）+ 桥接帧（某视频尾帧副本）。

| 测什么 | 断言 |
|---|---|
| `src()` 识别来源 | 3/3 正确 |
| 阈值分级 | mad<2 → high；2–5 → medium |
| **消歧**（两视频首帧相同） | 选链延续的那个 |
| **窗口比对**（抽帧非精确末帧） | 故意错开 2 帧仍能识别 |
| **中文路径** | 目录名含中文时 `imread_unicode` 不炸 |
| 废片判定 | 死胡同视频标为 discarded |
| **sanity check** | 全黑视频被标为"素材可能有问题"，而非"全片静止" |

### 层 2：真实素材回归（本地跑，素材不在仓库故条件跳过）

把本次实测结论固化为断言：

## 10. 风险与已知边界

| 风险 | 说明 | 应对 |
|---|---|---|
| **推断能力有天花板** | 只能从"文件间帧对应关系"推断；若某次重跑没留下桥接帧，或帧被覆盖，推不出来 | `confidence` 分级 + `review_needed`；`override` 逃生舱 |
| 早期会话无桥接帧 | 08–12 至 09–18 的 39 段里，可能只有《古老图书馆》有完整 `bridge_frames/` | 该会话正常推断；其余报 `review_needed`，不猜 |
| 新代码重蹈静默失败 | 这是本项目最严重的既有问题 | 第 7 节铁律②；代码评审时逐行检查 |
| 阈值不适用于其他题材 | 现有 0.00–1.97 vs 22–67 的间隔来自单一会话 | 阈值可配并留痕；合成 fixture 覆盖边界 |
| 比较陷阱被忽略 | 跨镜头数比较总数会误导 | 报告主推均值/比例（第 6 节） |

### 一条诚实声明

**本设计不提升视频质量。** 它只让"哪段用了哪张帧""接缝有多静止""还剩多少额度"变成可查的事实。

视频质量的修复（段尾冻结）在提示词层，是另一件事——本次诊断测出的基线
（接缝静止 4.04 秒 / 占全片 14.1%）正是验证那次修复的标尺。
