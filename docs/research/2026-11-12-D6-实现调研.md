## 0. 一句话结论（给排票的人）

D6 的工程量集中在**一个类**（`JobRunner`）和**一个模型**（`SessionState`/`SessionDetail`）：

- 长片的段循环没有现成骨架，`JobRunner` 目前只认识「阶段 1 / 阶段 2」两条执行路径
  （`api/jobs.py:469-497` 的 `_run`、`:537-569` 的 `_run_decision`、`:499-526` 的 `_resume_step`）。
- 段状态必须落在**顶层快照字段**（照 `jobs`/`action_items` 的先例
  `session_store.py:456-475`），不能塞进 `stage_state`——后者的键要过白名单与双向守卫
  （`session_store.py:102-135`、`tests/test_state_contract.py:1-50`）。
- 复用件（规划/写段/技术档/拼接）的签名都是「数据进、数据出」，与工作台解耦得不错
  （`segment_planner.py:305`、`segment_prompts.py:871`、`preflight.py:108`、`final_film.py:102`）；
  唯一**缺件**是「尾帧读图 vs `end_hook` 的自动判据」——CLI 侧这一层是人判
  （`ui/wizard.py:4729-4773` 的 `_judge_bridge_semantics`），D6 必须自己造一个。

## 2. JobRunner（阶段调用、进度、取消、插新步骤）

### 2.1 命令入口

| 入口 | 位置 | 要点 |
|---|---|---|
| `advance` | `api/jobs.py:170-216` | 每会话一把 `asyncio.Lock`（`:179`）；闸门判定与「写成 running」在 `store.mutate` 内一次完成（`:195-205`） |
| `resolve` | `api/jobs.py:218-426` | 幂等指纹 `:237-238`（`_resolve_fingerprint` `:64-72`）；kind 分支在 `_decide`（`:276-381`）；帧链 approve 不建任务，返回 `job=None`（`:250-255`、`:409-414`） |
| `_resolve_branch` | `api/jobs.py:428-452` | 锁外只读预判三条去路：`review` / `frame_gate` / `frames`（常量 `:78-80`） |
| `get_job` / `cancel` | `api/jobs.py:455-460` / `:462-463` | 取消只打标记（`_request_cancel` `:1259-1279`） |
| `ensure_can_advance` | `workbench_store.py:1363-1372` | `running`→`session_busy`、`completed`→`session_completed`、`awaiting_human`→`action_item_pending` |

**关键点**：`advance` 在 `awaiting_human` 上会被 `ActionItemPending` 拒（`workbench_store.py:1371-1372`）。
所以段循环**不能靠用户 advance 推进**，必须由 job 收尾自行起下一段（spec §5.3 的
「通过则起下一段写词 job」就落在这里）。

### 2.2 阶段 1/2 的执行与进度

- `_run`（`jobs.py:469-497`）：`_resume_step` 决定跑阶段 1 还是 2，`to_thread` 执行，
  `JobCancelled` / `Exception` / 正常三路收尾。
- `_resume_step`（`jobs.py:499-526`）：**只认识 stage1/stage2**，判据是「存在 `stage1_review`
  待办且已 approve」（`:516-525`）。D6 加 `segmenting` 必须在这里插分支，否则长片重试会
  重新进阶段 2。
- 进度事件 `{stage, node, status}`：
  - `_save_progress`（`jobs.py:1146-1167`）——带快照落盘（走 `mutate`），**stage 写死 `STEP_STAGE1`**
    （`:1158`）。段任务若要落 stage_state 得自己扩这条或另开一条。
  - `_emit_progress`（`jobs.py:1169-1176`）——只发事件（`record_events`），stage 是入参。
    阶段 2 的 started/done 全走它（`:829-841`、`:948-954`）。
- 阶段 1 的节点节拍器在 `on_step_done`（`jobs.py:618-638`）：节点名来自 `_STAGE1_CHAIN`，
  **取消检查在「报下一节点开始」之前**（`:633-638`，注释说明为什么不先发 started）。
- 桩分支：`_execute_stage1`/`_execute_stage2`/`_execute_revise` 开头各有一处
  `if self.fake_pipeline:`（`jobs.py:574-575`、`:767-768`、`:971-972`）。**互斥执行**，
  不是「真实路径里换一段回复」（`fake_pipeline.py:1-10`）。

### 2.3 收尾与「在哪插新步骤」

| 收尾 | 位置 | 现状 |
|---|---|---|
| `_finish_succeeded` | `jobs.py:1178-1208` | 落 `awaiting_human` + 一条 `stage1_review` 待办（先收旧 pending，`:1187-1192`） |
| `_finish_stage2` | `jobs.py:1210-1228` | **无条件** 落 `completed` |
| `_finish_cancelled` / `_finish_failed` | `jobs.py:1230-1242` / `:1244-1257` | 分别落 `cancelled` / `failed` |
| 调用点 | `jobs.py:490-495`（`_run`）、`:560-567`（`_run_decision`） | 两处都是 `if step/decision == stage2 → _finish_stage2` |

**D6-1 的插入点就是 `_finish_stage2`（`:1210-1228`）与它的两个调用点**：长片（`brief.duration > 10`）
成功后不能直接 `completed`，要落 `awaiting_human`/`running` 并发起规划任务。
注意 `_finish_stage2` 同时负责回写 `brief`（变体降级）与 `stage_state`（`:1216-1222`），改这里
必须保留那两件。

CLI 侧的长片判据可参考（**不调用**）：`ui/wizard.py:4367` `long_form = brief.duration > 10`。

### 2.4 取消、中断、启动对账

- 协作式取消：`threading.Event` 在节点边界检查（`jobs.py:633-637`、`:836-837`、`:951-952`、
  `:1072-1073`、`:1126-1127`、`:650-652`）。**不要承诺立即停止**（`jobs.py:6-9`、`workbench.md` 不变量）。
- `active-job.json`：写 `pid`/`job_id`/`started_at`/`node`（`jobs.py:1288-1297`），删前核对
  job_id 归属（`:1299-1305`）。
- `reconcile`（`jobs.py:1307-1359`）：启动时把 `running` 收成 `interrupted`，**不自动续跑**；
  判据「标记 pid 不是本进程且该进程还活着才跳过」（`:1328-1330`）；对账事件按 running 任务
  逐个记（`:1347-1352`）。
- lifespan 里调用顺序：`cleanup_assets` → `reconcile`（`api/app.py:89-94`）。

## 3. API 面

### 3.1 `SessionDetail` 与构造点

- 定义：`workbench_store.py:768-776`（`brief` / `last_event_seq` / `current_job` / `jobs` /
  `action_items` / `artifacts` / `assets`）。
- **唯一常规构造点**：`_detail_unlocked`（`workbench_store.py:1247-1264`）。它是
  `get_session`（`:1236-1245`）、`mutate`/`record_events` 的返回值、以及路由详情的共同出口。
- 另一个构造点：幂等重放时 `SessionDetail.model_validate(cached)`（`workbench_store.py:1199`）——
  **改 `SessionDetail` 字段必须保证旧缓存能校验通过**（给默认值），否则老幂等表会让建会话直接 500。
- `artifacts` 与 `assets` 都是**目录现扫**，不进快照（`workbench_store.py:1262-1263`、`:774-776`）。

### 3.2 duration 与错误码

- `DURATION_MIN_SECONDS = 4.0` / `DURATION_MAX_SECONDS = 10.0`（`api/routes/sessions.py:79-80`）。
- `DurationOutOfScope`（422 / `duration_out_of_scope`）`:83-88`；`_validate_duration` `:90-95`
  ——文案逐字写着「长片归 D6」（`:94-95`）。
- 校验在 `create_session` 最前（`:257`），**不是** pydantic `Field(ge/le)`（理由 `:76-78`：
  pydantic 的 422 没有 `code`）。
- 现有用例会因此变红：`tests/test_api_sessions.py:168-188`（`10.1`、`30` 现在必须仍被拒；
  改上界后要改这三档），且 `:170` 的 docstring 明确要求文案点名「长片归 D6」。

### 3.3 `action-items resolve` 的 kind 分支

- 请求模型 `ActionItemResolve`（`sessions.py:143-153`）：`decision` / `revisions` / `frames`。**没有 `video_asset_id`**。
- 路由层先做**载荷互斥**（`sessions.py:599-631`）：`decision=="approve"` 拒 revisions（`:600-602`）、
  `revise` 必带 revisions（`:603-611`）、`decision is None and revisions` 拒（`:612-614`）、
  `decision 与 frames 同时给` 拒（`:617-619`）、**两者都不给** → 422 `resolve 需要 decision（approve/revise）或 frames`
  （`:620-621`）。
  **这一条会直接拦住「只带 `video_asset_id` 的 `segment_video` 请求」**——#246 必须在这里
  加第三种合法载荷。
- 服务层 kind 分支在 `_decide`（`jobs.py:276-381`）：`stage1_review`（`:295-313`）、
  `frame_submission`（`:314-337`）、**未知 kind → `FrameInvalid("不认识的人工待办类型")`**（`:338-339`）。
- 错误类型：现有错配一律 `FrameInvalid`（`workbench_store.py:289`，422 / `frame_invalid`）。
  D6 的新码 `segment_video_invalid` 需要一个同形的新异常类。
- **幂等指纹不含 `video_asset_id`**：`_resolve_fingerprint`（`jobs.py:64-72`）只算
  `item_id/decision/revisions/frames`。不补的话，同一个 key 换视频会**重放第一次的响应**。
- 素材归属校验的现成模板：`resolve_frame_asset`（`workbench_store.py:1534-1553`）——
  「前缀必须等于 URL 里的 session（`:1542-1544`）+ 解析（`:1545-1549`）+ 类型收窄（`:1550-1552`）」。
  D6 的 `video_asset_id` 照这个写一份，把 `image/` 换成 `video/mp4`。

### 4.3 `artifact_id` 切分

`_split_artifact_id`（`workbench_store.py:888-897`）用 `rpartition("/")`，因为会话标识本身含斜杠
（`<主题>/GEN00N`，见 `_resolve` `:1133-1148`）。
**`segments/shot-01.md` 会让它切出 `name="shot-01.md"`、`session="<主题>/GEN00N/segments"`**
→ 后续 `name not in _ARTIFACT_KINDS` 直接 404。这就是 #245 要改「最长合法后缀匹配」的原因。

边界：`_resolve`（`:1133-1148`）拒绝对路径、`\`、空段、`.`、`..`、含 `:` 的段；
`_artifact_path`（`:1472-1481`）再 `resolve()` 一次并确认仍在根内（防符号链接逃逸）。

### 4.4 文本 1 MiB 与媒体 Range

## 8. 风险点（8 张票最可能互相冲突/踩坑的地方）

### R1. `JobRunner` 是唯一的交汇点，几乎每张票都要改它

`advance/resolve` 的闸门（`jobs.py:170-216`、`:218-426`）、`_resume_step`（`:499-526`）、
`_run`/`_run_decision`（`:469-497`、`:537-569`）、`_finish_stage2`（`:1210-1228`）、
`_decide` 的 kind 分支（`:276-381`）、`_resolve_branch`（`:428-452`）。
#244（规划 job）、#246（段循环）、#248（拼接）、#249（恢复）、#250（桩分支）**五张票都要动这个文件**。
建议先约定「段任务的执行/收尾函数」的签名与文件归属（新模块 vs `jobs.py`），否则并行必冲突。

### R2. `SessionDetail` / `SessionState` 加字段要同时改五处

`SessionState` dataclass（`session_store.py:456-475`）→ `save()` 的 payload（`:489-518`）→
`load_session` 的解析（`:585-600`）→ `workbench_store._state_with`（`:1288-1326`）→
`SessionDetail` 与 `_detail_unlocked`（`workbench_store.py:768-776`、`:1247-1264`）。
漏任一处：字段要么不落盘（`save` 只序列化显式列出的键），要么每次 `mutate` 后被重置（`_state_with`）。
另外**幂等缓存重放**会 `SessionDetail.model_validate(cached)`（`:1199`）——新字段必须有默认值。

### R3. 「自动起下一段」与 `advance` 闸门语义相反

`ensure_can_advance` 在 `awaiting_human` 上直接拒（`workbench_store.py:1371-1372`），而段循环要求
「resolve 之后由服务端自己起下一个 job」。现有 `resolve` 只在 `job is not None` 时起任务
（`jobs.py:409-421`），且 `_run_decision` 只认三种 decision（`:545-551`）。
#246 必须把 `segment_video` 这条新增分支**同时**接到 `_resolve_branch` / `_decide` / `_run_decision`
三处，并保证「被拒 → 重建待办 + `action_item.created` + 回 `awaiting_human`」走的是**同一次落盘**
（照 `_decide` 里帧链 `new_item` 的做法 `:351-357`、`:400-405`）。

### R4. 语义闸门在仓库里**没有自动判据**，D6 要新造一件

CLI 的段末对照是**人判**：`_judge_bridge_semantics`（`wizard.py:4729-4773`）把 `end_hook` 与
读图结果并排打印，然后 `_confirm(...)`。仓库里**没有**「文本 vs 读图描述」的自动比较器
（`grep end_hook` 的消费者只有规划/写段/拼接/导演台，`src/` 内无判定函数）。
D6 §8 要求 job 内自动对照并区分「被拒 vs 失败」，这是一个**全新件**：
它要有确定性的桩（否则 #250 的假读图没法判「不符」这条分支），而且它的**失败**必须落 `failed`
而不是 `被拒`（spec §5.4 第三种结局）。建议先把它做成独立纯函数 + 双分支用例，再接线。

### R5. 三个数字口径的陷阱

1. **段长上限两处不同**：规划档 base 是 4–10（`segment_planner.py:24`），而执行档校验是 4–15
   （`preflight.py:32-33`）。票面 D6-AC3 要求「最长段不超过 10 秒」——判据必须取**规划档**，
   别拿 `preflight` 的区间去断言。
2. **24 秒 ÷ 3 段 = 8 秒/段，不在 `H3_TIER_FRAMES`（4/5/6）里**（`preflight.py:40`）。
   #250 的桩视频与 #251 的真实验收都会命中 `segment_video_duration_unknown_tier`（**warning**，
   `:154-160`），不是 error。也就是说「真实闸门判定」在 8 秒段上只能证明**尺寸 + 区间**，
   证明不了档位——D6-AC13 的证据强度要如实写，别写成「闸门全程咬住」。
3. **`assemble_film` 的覆盖判据是 `>=` 不是 `==`**（`final_film.py:97-98`）。任何「各段之和 == 总时长」
   的断言都会在末段留余量时把全通过的片子判成伪产物（本仓已经咬过两次：`CONTEXT.md:302`
   的「成片」词条记的 #56/#57）。

### R6. 前端两处「静默不显示」

- `artifactGroup` 对未知 kind 返回 `null`（`artifactKinds.ts:14-25`），`ArtifactsTab.vue:29-31`
  与 `ReviewTab.vue:45` 都按 `=== group` 过滤 → **新 kind `segment_prompt` 不进
  `INTERMEDIATE_KINDS` 就一件都不显示、也不报错**。`KIND_ORDER.indexOf` 会给未知 kind 返回 -1
  （排最前），`KIND_LABELS` 缺失则回落到文件名（`:77`）。#245 要同时改这三张表。
- 新 Tab 要改 `stores/ui.ts:7` 的联合类型 + `SessionDetailView.vue:44-49` + 面板分支；
  `SessionDetailView.spec.ts`（15.1K）里有 tab 键盘/切换断言，会跟着动。

### R7. 十种事件 + 10 条 `EVENT_TYPES` 断言会把「加一种事件」变成红

`tests/test_api_assets.py:423`、`tests/test_step_machine.py:206-212` 写死 `len(EVENT_TYPES) == 10`。
段循环的所有状态变化必须挤进既有十种（`job.progress`/`job.succeeded`/`action_item.*`/`artifact.created`）。
D6 的 `segmenting` 只是**进度事件的 stage 取值**（`workbench_store.py:327-330` 派生自步骤机常量），
不是新事件类型——这条边界别越过。

### R8. `JOB_HISTORY_LIMIT = 20`（`jobs.py:58`）对 15 段偏紧

每段至少两个 job（写词、校验）＋规划＋拼接 ≈ 32 条；`_upsert_job` 只留最近 20 条（`:99-103`）。
超出的 job 从快照消失 → `get_job` 回 `job_not_found`（`:455-460`）。
前端目前只读 `current_job` 与 `jobs`（`SessionDetailView.vue:137-140`），影响面有限，但
**恢复/排障要读历史时只能翻事件流**。要把段进度表达在 `segments` 字段里，别再靠 job 历史。
