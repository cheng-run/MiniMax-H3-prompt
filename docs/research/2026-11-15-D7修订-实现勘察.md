# D7 修订（#279）实现勘察

> 为 #281–#285 五张实现票摸清接缝。**只读调研**，没有改动任何代码。
> 约定：代码指针一律写「模块 + 符号名」，不写行号（行号会漂且不报错）。
> 调研日期：2026-11-15。

## 一句话结论

现状不是「素材台账缺字段」，而是**素材集合的来源被写死在三条互不相干的入口上**：
创建表单拒收 refs、`_ref_brief` 把台账硬塞给阶段 1、`ensure_can_advance` 用 `brief.refs`
判起跑。要把它改成「阶段 1 派生」，必须同时松这三处，否则只改一处就会出现
「能起跑但 `ref_asset_registry` 仍然拿空 refs」或反过来的半接线。

## 1. 会话状态与台账形状

### 1.1 台账住哪

- **真源**：`session_store.SessionState.asset_ledger: tuple[dict[str, Any], ...]`，
  落 `<会话目录>/session.json`。读 `session_store.load_session`、写 `SessionState.save`。
- **形状是裸 dict，不是 `AssetRecord`**：`workbench_store._ledger_entry` 造条目，
  字段只有 `name / kind / number / asset_id / sha256 / round / status`。
  **没有** `path`、没有 `source`（来源）字段。`asset_id` 是 `<会话标识>/<16 位哈希>`，
  没有正本时为空串。
- **注意**：`asset_ledger.AssetRecord` 是**另一套**形状（CLI 侧，带 `path`/`sha256`/
  `source`/外部成本，且 `from_dict` 对未知字段**硬报错**）。工作台台账只在两处借用它：
  `JobRunner._card_record`（注入卡）与 `_materialize_director_asset_ledger`（导演台打包）。
  给工作台台账加字段时**不要**往 `AssetRecord` 里塞——那是 CLI 契约。

### 1.2 状态集合

`workbench_store` 的常量：

- `ASSET_LEDGER_STATUS_REGISTERED = "registered"`（已登记、没出词或被拒）
- `ASSET_LEDGER_STATUS_PASSED = "passed"`（校对通过＝定稿）
- `ASSET_PROOFREAD_KEY = "proofread_asset_id"`（已交图待校对的临时键，校对落定即 pop）

**没有** `pending` / `abandoned`，也**没有**来源字段。spec 要求的四态＋来源是纯新增。

### 1.3 「资产清单已派生」标记

**目前完全不存在**。而且不能随手塞一个顶层键：

- `SessionState.save` 只序列化**它自己的 dataclass 字段**，`load_session` 只读它认识的键；
  未知顶层键**静默丢弃**（与 LangGraph 丢未声明 state 键同型）。
- `WorkbenchSessionStore._state_with` 与 `mutate` 的可覆盖字段是**白名单**：
  `status / stage_state / jobs / action_items / brief / variant_downgraded / segments /
  asset_ledger`。新字段要同时进 `SessionState`、`save`、`load_session`、`_state_with`、
  `_detail_unlocked`（快照回显用不到则不必）。

### 1.4 读写台账的全部入口

| 入口 | 位置 | 行为 |
|---|---|---|
| 登记一行 | `WorkbenchSessionStore._register_ledger_entry` | 起跑锁 + 重名 + 重复内容 + 容量，然后 `_renumber_ledger` |
| 删除一行 | `WorkbenchSessionStore.delete_asset` | 摘登记 + 删正本 + 重编号 |
| 交图暂存 | `JobRunner._decide`（`ACTION_ASSET_IMAGE` 分支）写 `ASSET_PROOFREAD_KEY` | 只改内存副本，随 `mutate` 落盘 |
| 校对结算 | `jobs._settle_asset` | `round+1`、`status` 转 `passed`/`registered`、pop 校对键 |
| 推进度 | `jobs._asset_step_of` | 只看台账，「最大连续通过编号 + 1」 |
| 出词取件 | `JobRunner._picture_entry` | 按 kind+number 取一条 |
| DTO 回显 | `workbench_store._brief_out(brief, ledger)` | 台账 → `BriefOut.refs` |
| 注入卡 | `JobRunner._card_record` | 台账条目 → `AssetRecord`（要求 `asset_id` 可解析） |
| 导演台打包 | `JobRunner._materialize_director_asset_ledger` | 台账 → 临时 `asset-ledger.json` |
| 整片视频/音频容量 | `JobRunner._ref_film_media` | 台账里非 Picture 的条目 |

## 2. 起跑门槛（`asset_required`）

- **唯一判据**：`WorkbenchSessionStore.ensure_can_advance`。
- 条件：`route_uses_asset_ledger_fields(mode=..., director_mode=...)` **且**
  `not any(ref.kind == KIND_PICTURE for ref in detail.brief.refs)` → `AssetRequired`（409）。
- `detail.brief.refs` 来自 `_brief_out`，而 `_brief_out` 是**从台账现造**的
  （`brief.refs` 本身在创建工作台会话时恒为空）。
- r2v 与 ref 用同一个谓词 `route_uses_asset_ledger`（`brief_parser`），**没有按路线分叉**。
  spec 要求「ref 删门槛、r2v 保留」→ 这里必须新增分叉，且分叉判据不能再复用
  `route_uses_asset_ledger`（它把两条路线混为一谈）。
- 调用点只有一处：`JobRunner._new_job`（`api/jobs.py`，`self.store.ensure_can_advance(current)`）。

**利好**：`AssetRequired` 与 `AssetLocked` 都是 `WorkbenchError` 子类，错误码分别是
`asset_required` / `asset_locked`，改判据不影响契约形状。

## 3. `_ref_brief` 与执行点

`JobRunner._ref_brief(session)` 把台账里的 Picture 行按编号排序，造
`Brief.refs = [RefItem(picture, name, description="", path="")]`。注释明确写了
「用 `replace` 而非就地改，避免 `_finish_stage2` 写回时造副本」。

### 3.1 调用点（共 7 处，**全部都要过一遍**）

**实测调用点共 7 处**（`grep -n "_ref_brief("` 去掉定义本身）：

| # | 调用点（函数） | 阶段 | 新口径 |
|---|---|---|---|
| 1 | `_execute_stage1`（真实） | 阶段 1 | **不能再注入 refs**（spec 明确要求） |
| 2 | `_execute_stage1_fake`（桩） | 阶段 1 | 同上；桩另需能造 N 件清单 |
| 3 | `_execute_revise`（真实） | 阶段 1 修订重跑 | **同样不能注入**（它也是阶段 1） |
| 4 | `_execute_revise_fake`（桩） | 阶段 1 修订重跑 | 同上 |
| 5 | `_execute_stage2`（真实） | 阶段 2 | 保留，但只取**已定稿**行 |
| 6 | `_execute_stage2_fake`（桩） | 阶段 2 | 同上 |
| 7 | `_director_registry`（r2v） | 导演台规划 | 保留（r2v 不变） |

**注意**：段规划**不走 `_ref_brief`**——它走 `JobRunner._ref_plan_inputs`，直接读
`session.asset_ledger` 造 `(ref_meta, asset_paths)`。所以段规划不会因 refs 变化而变空，
但它会**把 `pending` 行也当参考素材**（`asset_id` 为空 → `resolve_asset_media` 抛错 →
被 `except` 吞掉只记一行 warning，`ref_meta` 里仍有那一行、路径缺失）。改成派生后
这一段必须加「只取已定稿行」的过滤，否则接线卡上会出现没图的槽。

**这一条是最大的接线风险**：`_ref_brief` 被 4 个阶段 1 调用点共用（真实/桩 × 首跑/修订），
而 spec 只对「阶段 1」说了一句话。两种改法：

1. 给 `_ref_brief` 加参数（如 `include_refs: bool`），阶段 1 四路传 False；
2. 拆成两个函数（`_ref_brief` / `_ref_brief_without_refs`）。

无论哪种，漏改「修订重跑」那两处会让「审查后改一句」重新吃回注入 refs，
`ref_asset_registry` 走「用户登记为准」支路，资产图词与派生的台账再次脱钩——
而首跑路径的测试全绿。

### 3.2 「用户登记为准」那一支

`generation.ref_asset_registry`：**`if brief.refs: return _with_merged_descriptions(sorted(brief.refs))`**
——这一支在 `route_emits_asset_prompts` 守卫**之前**返回。所以只要阶段 1 拿到非空 refs，
编号、名字、顺序就全由台账决定，设计师清单里的名字被彻底绕过。这正是死锁的根因。

反向：阶段 1 不注入 refs 后，`ref_asset_registry` 会走派生支路——它按
`asset_prompts_for(brief, state)` 的产出 + 剧本里语义名的首次出场位置排序。
**阶段 1 自己还是需要 `asset_prompts_for` 的产物**来写资产图词，所以派生清单在阶段 1
内部是有的（在 `state` 里），只是不经过 `brief.refs`。

## 4. 阶段 1 收尾的那一次写入

**唯一位置**：`JobRunner._finish_succeeded(session_id, job_id, stage_state)`。

它现在做三件：

1. `self._succeed_job(detail, job_id)`；
2. 收掉旧的 pending `stage1_review`，挂一个新的；
3. 返回 `{status: awaiting_human, stage_state, jobs, action_items}`。

事件两条：`job.succeeded` + `action_item.created`。

派生落行要**在同一处**做（spec：「与 `stage1_review` 待办同一次 mutate」）。

**注意 `_apply` 拿到的是 `SessionDetail`**，不是 `SessionState`——要台账得用
`detail.asset_ledger_snapshot()`（返回 `list[dict]` 副本），写回用返回字典里的
`asset_ledger` 键。

**两条入口都走这里**：真实阶段 1 与 `_execute_stage1_fake` 都会落到 `_finish_succeeded`
（`_run` 的收尾分支）。所以派生只需实现一次。

**修订重跑不落这里**：`_execute_revision_rerun` 走 `_finish_succeeded` 吗？——它
返回的是 `{"state", "brief", "rerun_from"}` 的另一种收尾；派生口的幂等性要求因此必须
靠「台账已有 derived 行就不动」，不能假设只跑一次。

## 5. 资产图词的来源与清单

- `generation.asset_prompts_for(brief, state)` → `image_prompt_variants(state, canvases)`，
  读 `state` 里的三类键（`character_image_prompts` / `prop_image_prompts` /
  `scene_image_prompts`，具体键名由 `ASSET_KIND_FIELDS` 决定）。
- `generation.asset_prompt_for(brief, state, name)` 按语义名取一条；
  取不到抛 `AssetPromptMissing`，文案已带「现有：A、B」。
- **清单块解析**在 `asset_manifest.py`：`MANIFEST_FENCE = "asset-manifest"`，
  `split_manifest_reply` 返回 `ManifestSplit(body, names, problem, duplicates)`。
  类内重名由解析器判；跨类重名由设计合并处守卫判（`graph/nodes.py` 附近）。
- **对账点**：现在 `AssetPromptMissing` 的方向是「台账名 → 词里找不到」。spec 要求
  反过来（「词/清单 → 台账缺件、多件、改名」）。**同一个异常类型可复用**，但新增的
  三个方向（缺件/多件/改名）需要在文案里同时点名「现有」与「缺失」。

**关键**：`asset_prompts_for` 是**按路线**判的（`route_emits_asset_prompts`：ref 恒真、
导演台只 r2v 真），所以派生口天然只对 ref 与 r2v 生效。r2v 不走派生（它的台账由上传建立），
所以派生口要再按 `brief.is_ref` 收窄——但 `brief.is_ref` 与 `route_emits_asset_prompts`
是两个判据，别混用。

## 6. 素材循环

### 6.1 步骤机（`step_machine.py`）

- 阶段标签：`STEP_ASSET_LOOP = "asset_loop"`，在 `STEPS` 里排第 2（stage1 → asset_loop →
  stage2 → packing → segmenting）。**`STEPS` 的顺序派生 `workbench_store._PROGRESS_STAGES`**，
  加新阶段要同步（但本次不需要新阶段，`asset_extra` 只是新待办）。
- 待办常量：`ACTION_ASSET_IMAGE = "asset_image"`。
- 决议常量：`DECISION_SUBMIT_IMAGE = "submit_image"`（内部词，接口上靠 `asset_id` 分型）。
  新增 `abandon_asset` 需要：新常量 + `ActionItemResolve.decision` 的 `Literal` 加一项 +
  `_decide` 里的 asset_image 分支 + `_branch_of`（只读预判，`_BRANCH_ASSET_LOOP` 已存在）。
- `resolve()` 只管 stage1_review 的 approve/revise；asset_image 不进 `step_machine.resolve`。

### 6.2 执行（`api/jobs.py`）

- 推进度：`_asset_step_of(ledger)` → `(ASSET_STEP_WRITE | ASSET_STEP_PROOFREAD | ASSET_STEP_DONE, number)`。
  跳过 `abandoned` 行的改动**只在这一处**（外加 `_settle_asset` 不把它当失败）。
- 分派：`JobRunner._run` 的 `STEP_ASSET_LOOP` 分支 → `_asset_step` → `_execute_asset_write`
  / `_execute_asset_proofread`。
- 收尾：`_finish_asset_write`（挂 `asset_image` 待办）、`_finish_asset_proofread`
  （结算 + 接下一件或转 `advance` job）。
- **循环结束的判据**：`_finish_asset_proofread` 里 `step != ASSET_STEP_DONE` 决定接
  `asset_loop` 还是 `advance`。补交待办（`asset_extra`）要插在「DONE 之后、advance 之前」，
  即把这里的 `"advance"` 换成「起 `asset_extra` 待办 / 或者直接 advance，看是否已解」。
  同时 `_resume_step` 的 `route_uses_asset_ledger and _asset_step_of != DONE` 判据也要扩
  （否则重启后不知道要补交）。

### 6.3 「换一张图」

现状**没有**「已定稿后重开」的入口：`_settle_asset` 一旦 `passed`，`_asset_step_of`
就跳过它。要支持「循环内对已定稿件重开」，需要：
- 台账行退回 `registered` 并保留 `round`；
- 重挂同一件号的 `asset_image` 待办；
- `_asset_step_of` 的「最大连续通过编号 + 1」要允许「人为指到前面某件」。

**这是一个 spec 未给出算法的新能力**（spec 只说「该行退回未定稿、重走校对」）。
实现票要自行决定：是新增一个 `reopen` 端点，还是靠某个决议。**建议在 #282 里单列越权假设**。

## 7. `asset_locked` 与上传端点

- 判据：`WorkbenchSessionStore._ensure_asset_writable(session)`：
  `route_uses_asset_ledger(session.brief) and session.status != "created"` → `AssetLocked(409)`。
- 只在**带语义名登记**的路径上生效（`_register_ledger_entry` 与 `delete_asset`）；
  不带语义名的普通素材上传不受限（`WorkbenchSessionStore.store_asset` 的 `registering` 分叉）。
- 路由层：`api/routes/assets.py`（`POST/GET/DELETE /sessions/{id}/assets`），
  上传前先调 `ensure_upload_target`（只管 legacy）。
- 前端：`AssetsTab.vue` 的 `locked` computed 与 upload 输入框 `:disabled` 是**第二份**判据
  （与后端同一条规则，两处各写一遍——改「位置锁」时前端也要跟着改，否则界面先放行、
  提交才 422）。

**位置锁要新增的东西**：谁算「当前待办那一件」——后端能算（`_asset_step_of`），
前端只能从快照的待办推断。建议后端在拒绝时点名「当前是第 N 件」，前端按待办卡判断。

## 8. 容量闸门

- 数字契约唯一真源：`ref_capacity.py`（`MAX_PICTURES=9` / `MAX_VIDEOS=3` /
  `MAX_AUDIOS=3` / `MAX_FILES=12`），函数 `check_reference_capacity(items, where=...)`。
- 错误包装：`workbench_store._check_ref_capacity(entries, where=)` → `RefCapacityExceeded`
  （422 `ref_capacity_exceeded`）。
- 调用点：`_register_ledger_entry`（登记时）、`store_asset` 的快速失败（搬字节前）、
  `ref_segments._check_segment_capacity`（逐段，`film_media=` 让工作台台账复用同一判据）。
- **spec §8 说「位置不变，判据改成按交回节奏算」**：现在容量只在「登记」时算；
  派生落 N 行 `pending` 时，N 件本身就是容量的一部分（如果设计师写了 10 个人物，派生
  就该当场超限）。这一点 spec 没明说，**建议在 #281 明确**：派生时是否跑一次容量闸。

## 9. 待办与事件契约

- **事件闭集**（`workbench_store.EVENT_TYPES`，10 种）：`session.created` / `job.started` /
  `job.progress` / `job.succeeded` / `job.failed` / `job.cancelled` / `job.interrupted` /
  `action_item.created` / `action_item.resolved` / `artifact.created`。
  ── `asset_extra` 与 `abandon_asset` **不需要新事件类型**，复用 `action_item.*`。
- **待办 DTO**：`workbench_store.ActionItemOut`（`item_id / kind / status / created_at /
  resolved_at / decision / revisions / segment_index / asset_index / start_asset_id /
  end_asset_id / video_asset_id / pack_asset_id / reason`）。
  新增 `asset_extra` 后，补交的视频/音频要不要在待办上回显，需要决定（spec 只说载荷
  `asset_id` + 「没有」）。
- **新增待办 kind 要动的地方**（把这条清单当 checklist）：
  1. `step_machine.ACTION_*` 常量 + `__all__`；
  2. `api/routes/sessions.py` 的 `ActionItemResolve.decision` `Literal`（若用显式 decision）；
  3. `api/jobs.py` 的 `_branch_of`（只读预判）+ `_decide`（锁内判定）+ 收尾函数；
  4. `api/jobs.py` 的 `_resume_step`（重启后能重建「在等谁」）；
  5. 前端：`SessionDetailView.vue` 的 `pendingXxxItem` computed + 组件 + `progress.ts`
     的 `PENDING_HINTS`（未知 kind 会退化成通用文案）；
  6. 契约：`scripts/export_openapi.py` → `contracts/openapi.json` → 前端 `generated.ts`。
- `action_item.created` 的 payload 规则在 `workbench_store._PAYLOAD_RULES`（按 kind 收
  `asset_index` / `segment_index` 等）。加新键要同步改。

## 10. 前端素材分区

  - 容量条：`refCapacity.ts` 的 `capacityRows(refs)` + `REF_KIND_LABELS`

## 11. 桩管线

- 阶段 1 桩：`fake_pipeline.stage1_state(brief, previous)`
  ——**它是从 `brief.refs` 读 reference 列表的**（`refs = sorted(brief.refs, ...)`），
  再按 ref 名字造剧本台词、分镜表、`character_image_prompts`。
  → 阶段 1 不再注入 refs 后，**桩会造出 0 件资产**，整个素材循环空转、E2E 直接崩。
  **这是 #285 的核心改动**：需要一个「指定件数」的旋钮（环境变量或 `previous` 里的键），
  并支持「故意漏一件」这一档。
- 校对桩：`fake_pipeline.asset_proofread_verdict(number, first_number, round_no)`
  第 1 件第一轮不通过、其余通过（判据是轮次，不是调用次数）。
- `JobRunner._execute_asset_proofread_fake` 只换「读图 + 改写」，台账转移仍走
  `_finish_asset_proofread` 的真实代码。
- 桩产物形状与真实一致（`asset_prompt_text` 造词，落盘走 `store.write_text_artifact`）。

## 13. 与 spec 不一致之处（最重要的一节）

1. **`_ref_brief` 有 7 个调用点，spec 只说了「阶段 1 不注入」**。其中「修订重跑」
   是**两个**调用点（`_execute_revise` / `_execute_revise_fake`），spec 没点名。漏改会让
   「审查后修订」重新走回用户登记支路，资产图词与派生的台账脱钩。**实现时请把 3.1 的
   表逐条过。** 另外段规划走的是 `_ref_plan_inputs`（直接读台账、不经 `_ref_brief`），
   它要把 `pending`/`abandoned` 行滤掉。

2. **「资产清单已派生」目前没有任何落点**，且会话文件的顶层键是白名单（未知键静默丢弃）。
   它不是「加一个字段」那么简单：`SessionState` + `save` + `load_session` + `_state_with`
   四处都要动。spec 说「记在会话上」，但没说记成顶层键还是台账里的一个标记行——
   **建议顶层键**（它是会话级事实，不是某一件资产的事实），但需要协调会话确认。

3. **`asset_extra` 的「编号走独立标签」在代码里不存在**：`format_tag` 只有
   `<Picture N>` / `<Video N>` / `<Audio N>` 三种。现有的视频/音频**共用**同类编号
   （`_next_number(ledger, kind)`）。spec 说「不占 Picture 号段」，这在现有实现里
   天然成立（编号按 kind 分桶）；但「独立标签」要不要给补交件一个**新的引用名**
   （如 `<Extra Video 1>`），代码里没有对应物——**建议按现有 `<Video N>` 处理**，
   并在票面记「越权假设」。

4. **「循环内换一张图」没有现成入口**：`_asset_step_of` 的「最大连续通过编号 + 1」
   是单调的，`_settle_asset` 一旦 `passed` 就跳过。要做「退回未定稿」必须新开一个动作
   （端点或决议），spec 只说「该行退回未定稿、重走校对」，没给触发形状。
   **这是 #282 最需要裁定的一条。**

5. **`AssetRecord.from_dict` 会对未知字段硬报错**。如果为了存 `status` / `source`
   去扩展 `AssetRecord`，导演台打包（`_materialize_director_asset_ledger`）与注入卡
   （`_card_record`）的读回都会炸。**工作台台账是裸 dict，加字段只改 `_ledger_entry`
   与读它的地方**；`AssetRecord` 保持不动。

6. **`_brief_out` 现在无条件按台账回显 `refs`**，且 `RefOut` **没有** status/source 字段。
   #283 要在素材分区显示「已定稿/已放弃/待办」，**前端需要新的 DTO 字段**
   （`RefOut` 加 `status` 与 `source` 是最小改动），否则前端只能从待办列表反推，
   而「已被放弃但顺序在后面的件」在待办里不存在。
   ——**这一条会影响契约**（`contracts/openapi.json` 与 `generated.ts`），要跑契约漂移检查。

7. **`ref_asset_registry` 的派生支路仍按剧本语义名排序**（`_appearance_key`），而 spec 说
   「编号＝剧本出场序」。两者一致，但**前提是 `state["script"]` 里有那个名字**；桩管线的
   剧本台词是按 ref 名字现编的，一旦 refs 为空，剧本里也不会有名字，排序退化为枚举序。
   真实路径同样有这个风险：如果设计师写的名字在剧本里没出现（比如只出现在分镜表），
   编号会排在最后。spec 说「出场序」时没有定义「出场」的判据——**沿用现有
   `_appearance_key`（剧本首次出现）即可**，但要在票面记录。

8. **`ensure_can_advance` 用 `brief.refs` 判起跑，而 `brief.refs` 是台账的投影**。
   改成「ref 不判、r2v 判」时，不能简单地删掉判据——r2v 的台账也是同一份
   `asset_ledger`，但 r2v 的素材来自上传，`_brief_out` 同样会回显它们。
   **最稳的写法**：判据改成「`route_uses_asset_ledger` 且 `brief.director_mode == "r2v"`
   且台账无 Picture」——而不是「ref 一律放行」，因为未来若 ref 也开了预上传，会回归。
